package.nix：一个函数，三类参数#

pkgs/firn-hello/package.nix 有 52 行，我分五块看。第一块是它的签名和 mkDerivation 的开头：

它是一个函数，参数是一个属性集，五个名字里 lib、stdenv、pkg-config、zlib 是“依赖”，nixpkgs 里有同名的属性；greeting 是“旋钮”，nixpkgs 里没有叫这个名字的包，所以它走默认值 "Hello"，除非有人显式传一个。谁来区分这两类，下一节讲。

mkDerivation 收到的是 (finalAttrs: { ... })，一个函数而不是一个属性集。finalAttrs 是这组属性自己的最终版本，包括别人事后 overrideAttrs 加上去的改动，和第 3 篇的 fix 是同一个技巧；后面有一节专门看它在源码里长什么样。

第二块是源码：

第三块是构建，这一块最啰嗦：

makeFlags 传给 make：PREFIX 用 placeholder "out"（求值时输出路径还没有定，它先生成一个占位符，构建时才换成真路径），ZLIB_LIBS=-lz 是上一节那个后门，覆盖 pkg-config --libs zlib 的结果。

问候词走的是 env.NIX_CFLAGS_COMPILE，不是 makeFlags 里的 CFLAGS=...：Makefile 里的 CFLAGS ?= -O2 -Wall -Wextra 会被命令行的 CFLAGS= 整个替掉，而 NIX_CFLAGS_COMPILE 是 cc-wrapper 在编译器命令行末尾追加的，不动 Makefile 里的警告选项。strictDeps = true 让 nativeBuildInputs（构建机上跑的工具，pkg-config）和 buildInputs（链进产物的库，zlib）严格分开，第 12 篇讲交叉编译时会用到这个区分。

meta 不影响构建出来的东西，它是写给人和工具看的：一句话描述、许可证、nix run 找哪个可执行文件（mainProgram，src/nix/app.cc 第 111 到 113 行先取 meta.mainProgram，没有再取 pname，再没有才从 name 里拆）、在哪些平台可用。我把 meta 实际输出的 JSON 放在后面 nix log 那一节旁边。

override 与 overrideAttrs：改参数，还是改属性#

callPackage 返回的东西带 .override，是上一节最后留下的线头。它来自 makeOverridable，第 152 行开始的那个函数。我只摘和这一篇相关的几行：

第一行是 override 的全部实现：拿到新参数 newArgs（可以是属性集，也可以是一个吃旧参数的函数），和最初调用时的参数 origArgs 合并，再 makeOverridable f 重新调一遍 package.nix 里那个函数。customisation.nix 的第 175 到 178 行把 override 加到结果上，第 192 行给 overrideAttrs 套了一层：先让 mkDerivation 自己的 overrideAttrs 去改属性，然后再 makeOverridable 一次，这样 .overrideAttrs 之后的结果仍然有 .override。

所以 override 和 overrideAttrs 改的是调用链上两个不同的位置：

  • override { greeting = "Hallo"; } 重新调用 package.nix 的函数，改的是它的参数：lib、stdenv、pkg-config、zlib、greeting。它只能改 package.nix 的作者愿意暴露为参数的东西，但可以换依赖 (override { zlib = otherZlib; })。
  • overrideAttrs (old: { ... }) 改的是 package.nix 里传给 stdenv.mkDerivation 的那个属性集：version、src、patches、env、installCheckPhase，任何属性。代价是你得知道那些属性长什么样。

rebuilt 为什么不能构建#

这里有个我没想到的结果。实验只对五个变体求值，没有构建它们（override_kinds.sh 只 nix build 了 base 和 overridden）。我把 rebuilt 和 bumped 真的构建了一遍（手敲，不在 lab/ch10/ 里）：

日志的最后一行是 Running phase: installCheckPhase，后面什么都没有：test "$first" = ... 不相等，退出 1。原因在 package.nix：greeting 这个参数被用了两次，一次在 env.NIX_CFLAGS_COMPILE，一次在 installCheckPhase 的字符串里。override { greeting = "Moin"; } 会同时改两处，因为两处都是从同一个参数插值出来的；而 rebuilt 用 overrideAttrs 只替换了 env，installCheckPhase 里那个字符串在 package.nix 被调用的时候就已经插值成 Hello, nix, from firn-hello 0.1.0 了，overrideAttrs 够不到它。程序打印 Moin, ...，检查期待 Hello, ...，构建失败。

这是 override 和 overrideAttrs 区别最干净的一个例子：override 在数据流的上游改，凡是从这个参数算出来的东西都跟着变；overrideAttrs 在下游改，只改你指到的那个属性。

理由不在 Nix 里，在 GitHub 那一边。GitHub 自己的说法是，它不保证自动生成的归档的校验和稳定（就是 Releases 页面上的 “Source code (tar.gz)”）：2023 年 1 月 Git 改了归档的默认压缩，内容没变，校验和变了，GitHub 随后表示先把这个改动回退；如果需要稳定的校验和，应该把归档作为 Release 资产上传。.tar.gz 的字节取决于 tar 和 gzip 怎么压，目录的 NAR 只取决于文件。fetcher 对目录算 hash，就绕开了压缩层的变动，nixpkgs 的注释说的“hash 更稳定”（上面那个第 127 行）就是这个意思。

tag = "ch10" 这样的标签是可以被挪动的，hash 是它的保险：标签被挪到别的 commit，抓下来的目录变了，hash 对不上，构建失败而不是悄悄换内容。第 11 篇要用的正是这个：cairn 的 src 是 fetchFromGitHub { owner = "bfmhno3"; repo = "cairn"; tag = "ch10"; hash = ...; }。

上面那条 gcc 命令里的 gcc，不是直接的 GCC。stdenv 里的 gcc 是 cc-wrapper 生成的脚本，真的编译器在它里面，你看不到的那部分工作都在这个脚本里。lab/ch10/rpath.sh 看三处：构建环境里的变量、结果文件里的 ELF 头、和闭包。

先是构建环境。nix develop --file nix/pkgs.nix firn-hello 给出 firn-hello 的构建环境（第 9 篇那种），实验在里面打印几个变量：

NIX_CFLAGS_COMPILE 里有我关心的两样：-DFIRN_GREETING="Hello"（package.nix 的 env.NIX_CFLAGS_COMPILE）和 -isystem .../zlib-1.3.2-dev/include（stdenv 的 setup hook 看到 zlib-dev 有 include 目录，就追加了 -isystem）。真实的值里还有一个 -frandom-seed=...，NIX_LDFLAGS 里还有一个指向构建目录的 -rpath 项，rpath.sh 用 sed 把它们去掉了。cc-wrapper 在命令行后面追加它们：cc-wrapper.sh 第 198 行，extraAfter=(... $NIX_CFLAGS_COMPILE_@suffixSalt@)。

NIX_LDFLAGS=-L.../zlib-1.3.2/lib：bintools-wrapper 的 setup hook看到 zlib 的 out 输出里有 lib/lib*，就加一个 -L。注意只有一个，是 out 的，不是 static 的：从这个结果看，buildInputs = [ zlib ] 没有把 static 输出带进 NIX_LDFLAGS。

上面最后三行 pkg-config --libs zlib 的输出里，-L 的顺序是 static 在前。这是 zlib.pc 里写的，再看两个目录里各有什么（手敲，不在 lab/ch10/ 里）：

Libs: -L${libdir} -L${sharedlibdir} -lz，libdir 在 nixpkgs 的 zlib 里指向 static 输出，sharedlibdir 指向 out。nixpkgs 把静态库拆到单独的输出，是为了避免“上游这个有问题的行为带来的闭包体积惩罚”（注释里说，zlib 的 ./configure 总是会构建静态库，而 --static 是 --disable-shared 的别名；nixpkgs 用一个单独的 static 输出装静态库，对应的开关是 splitStaticOutput，第 21 行）。而 -lz 前面是两个 -L，按 ld 的搜索规则，它一个目录一个目录地找，每个目录里 libz.so 和 libz.a 都接受，第一个有的就用。static 目录里只有 libz.a，排在前面，所以 -lz 就选了静态库（这是我从结果反推的，没有去读 ld 的源码；下面不覆盖时的 NEEDED 里没有 libz.so.1，和这个解释一致）。

这就是为什么 package.nix 里有 "ZLIB_LIBS=-lz"。不覆盖它，Makefile 会用 pkg-config --libs zlib，得到上面三行，链接器就静态链接了 libz.a。不覆盖会怎样，lab/ch10/fixtures/firn_hello_default_link.nix 保留了那个版本，它把 makeFlags 里的 ZLIB_LIBS= 去掉：

3. make check 打印的是 running 0 flake checks...。这是不是说明 pkg-firn-hello 没有被检查？

参考答案

不是，它说明那些检查不需要再构建。nix flake check 先求值每个检查的 derivation（输出里的 derivation evaluated to ... 行，包括 pkg-firn-hello 和 pkg-firn-hello-hallo），再调 queryMissing，只构建 willBuild 里的（src/nix/flake.cc 第 802 到 813 行；源码注释说，已经能从缓存拿到的输出不再构建，因为 flake check 只需要验证“能构建”）。pkg-firn-hello 刚在这台机器上构建过，已经在 store 里，所以是 0。--dry-run 能看到同样的结论（手敲，不在 lab/ch10/ 里）：

没有 will be built，没有别的输出。换一台没有构建过的机器，像 pkg-firn-hello 这种不在任何公共缓存里的检查会先被构建。
