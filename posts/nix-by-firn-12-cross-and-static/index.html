第 11 篇结尾我留了一个问题：firn-hello 换成 musl 静态链接，闭包会不会比 Pebble 那个 1.8 MiB 的二进制还小。我现在有答案了，而且答案比问题怪：静态版的二进制反而更大。

glibc 版的闭包是 37,866,984 字节 (36.1 MiB)，静态版是 346,416 字节 (338.3 KiB)，相差 109 倍。Pebble 的二进制本身是 1,883,160 字节，整个静态闭包只有它的 18.4%。但静态版的二进制是 61,400 字节，比动态版的 16,000 字节大 3.8 倍：二进制胖了，闭包却瘦了两个数量级。这一篇我要把这个反差拆开，顺手把 Nix 里最容易被当成魔法的一套东西学明白：build、host、target 三个平台，pkgsCross 和 pkgsStatic，以及让 nativeBuildInputs 和 buildInputs 在同一个包里指向不同架构的 splicing。

本篇检查点

这一篇结束时，Firn 仓库的标签 ch12 里：flake.nix 的 packagesFor 多了三个只在 x86_64-linux 上存在的包 firn-hello-static、firn-hello-musl 和 firn-hello-aarch64（git diff --numstat 显示 24 行新增、12 行删除，删除的大多是原有几行因为接上了 // 而改过的缩进）；README.md 的输出表多了一行（1 行新增）；checks.x86_64-linux 因此从 11 个变成 14 个（每个包一个 pkg-<name>）；lab/ch12/ 下有 9 个实验（7 个 .sh 和 2 个 .nix）和 1 个 fixture 文件。pkgs/firn-hello/package.nix、overlays/default.nix 和 default.nix 没有变：三个交叉和静态构建没有暴露出这个包里的任何 bug。make ch12 全部 ok。 涉及的 Nix 特性：stdenv.buildPlatform、hostPlatform、targetPlatform，lib.systems.elaborate 与 lib.systems.examples，pkgsCross、pkgsStatic、pkgsMusl，splicing (__spliced, buildHost, hostTarget)，strictDeps，doInstallCheck 与 canExecute，stdenvAdapters.makeStatic，propagatedBuildInputs，nix develop --file，nix log，nix path-info，qemu-user。 前置：第 11 篇：打包真项目：Cairn、Sift 与 Pebble。这一篇用的包是第 10 篇的 firn-hello，依赖分类是第 7 篇讲过的偏移量，只是这次真的有两个平台了。 终稿与否：lab/ch12/* 在这里就是终稿；README.md 和 flake.nix 之后每次加包还会改。

三个平台字段：build、host、target#

这三个词不是 Nix 发明的，是 autoconf 留下来的。Nixpkgs 手册的交叉编译一章开头就写着 Nixpkgs 遵循 GNU autoconf 的惯例。Autoconf 手册里，./configure 有三个选项：--build 是配置和编译这个包的那台机器的系统类型，--host 是这个包运行的那台机器，--target 是包里任何编译器类工具产出的代码要运行的机器，手册给它的标注是 rarely needed。--host 和 --build 不同，就进入交叉编译模式；手册还说，这时构建工具默认带 host-type- 前缀，比如 host-type-gcc。

一个字符串怎么变成一个平台#

lib.systems.elaborate 把一个只有 config 或 system 的最小描述展开成 platforms.nix 输出里的那些字段。elaborateAarch64Linux 那一组有三个值得停一下的地方：

  • linuxArch = "arm64"：Nix 管这个 CPU 叫 aarch64，内核源码树里的目录叫 arm64。elaborate 的工作之一就是记住这种别名，lib/systems/default.nix 的 334 到 345 行是 linuxArch 的映射，elaborate 本身从 88 行开始。
  • isStatic = false：这个字段对 aarch64-linux 是 false，318 行的定义是 final.isWasi || final.isRedox，也就是说它默认只对没有动态库的平台为真，pkgsStatic 是通过 crossSystem 显式把它设成 true 的。
  • nativeCanExecute = false：我这台 x86_64 的 buildPlatform 能不能直接执行 aarch64 的二进制。这个值来自 canExecute：

组合起来的包集，缓存可能就没有了。同样的检查，对 pkgsCross.aarch64-multiplatform.pkgsStatic.firn-hello（交叉到 aarch64 的 musl 静态）（手敲，不在 lab/ch12/ 里）：

binfmt：让 qemu 自动出场#

run_aarch64.sh 里我显式写 qemu-aarch64 ./firn-hello。NixOS 有一个选项把这一步交给内核：boot.binfmt.emulatedSystems = [ "aarch64-linux" ];（NixOS 选项）。它向内核的 binfmt_misc 注册一条规则：看到 aarch64 的 ELF 魔数，就用 qemu 解释器启动它。启用之后 ./firn-hello 直接就能跑，run_aarch64.sh 里那个 Exec format error 就不会出现。

同一个选项还会把这些平台写进 nix.settings.extra-platforms（274 到 276 行，由 addEmulatedSystemsToNixSandbox 控制，默认 true），于是 Nix 愿意在本机“原生”构建 system = "aarch64-linux" 的 derivation，放在 qemu 里跑。那条选项的说明里有一句警告，我原样引：“the builder can execute all emulated systems within the same build, which introduces impurities in the case of cross compilation”：交叉编译时，构建过程可以直接执行目标平台的程序，这是 strictDeps 想防住的那类事情（pkg-config 偏偏能跑了）又被放回来。

nixpkgs 自己也用这个思路：lib.systems 里的 emulator（lib/systems/default.nix 的 104 到 125 行）按平台挑一个模拟器，Linux 到 Linux 就是 qemu-user（手敲，不在 lab/ch12/ 里）：

我这台机器没有启用 binfmt（binfmt_misc 里的条目数是 0），所以这一段只是读源码得来的，没有在这台机器上运行 emulatedSystems。

让我意外的事#

我原来以为这一篇讲的是“怎么让 Nix 编出别的架构的程序”，写完发现真正的内容是“你以为的那几个词，在 nixpkgs 里各指什么”。四件事：

名字里带 cross 或 static 的包集，不一定在交叉编译，名字里带 musl 的，也不一定不在。 pkgsMusl 是用 musl 原生构建的整个包集，spliced = false；pkgsStatic 是从 glibc 到 musl 的交叉，spliced = true；pkgsCross.gnu64.firn-hello 的 drvPath 和原生 firn-hello 的相等，因为 crossSystem 展开后等于 localSystem，nixpkgs 就当它是原生。我是靠 drvPath 才发现这一点的，包名里没有任何提示。

静态链接的闭包不是 0。 firn-hello-static 的二进制里没有任何 /nix/store 路径（strings | grep -c 是 0），闭包却有三个路径、346,416 字节。其中 82.0% 是 zlib-static 的 dev 和 out，原因是静态 stdenv 的 propagateBuildInputs 把每个 buildInputs 改成了 propagatedBuildInputs，nix-support/propagated-build-inputs 里的那一行被引用扫描器当成了依赖。我用 overrideAttrs 把它拿掉过，闭包就是 1 个路径，二进制不变，输出不变。

放错依赖类别，原生和交叉都会失败，只是“要不要同时拿掉 ZLIB_LIBS=-lz”决定了你看不看得见。 package.nix 里有 strictDeps = true，有了它，原生的 buildInputs 里的 pkg-config 也进不了 PATH。变体 1（保留 ZLIB_LIBS=-lz）退出码是 0，只在日志里留一行 pkg-config: command not found：这类错误会被一个无关的补丁静静盖住，而这个补丁在第 10 篇里是我自己加的。

交叉构建环境里没有 gcc。 cross_cc_name.sh 输出里的 gcc -dumpmachine 打印 x86_64-unknown-linux-gnu，容易让人以为 PATH 上还有构建机的编译器。清空外层 PATH 之后，交叉构建环境里根本没有无前缀的 gcc：那两行是 Firn 开发 shell 里的 x86_64 gcc 漏进来的。
