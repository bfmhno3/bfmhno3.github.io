一行字变成 argv 的路上#

第 1 篇里我们看到，shell 最后做的事是 fork 一个子进程，再 execve(path, argv, envp)。argv 是一个字符串数组，程序（C 里的 main(int argc, char **argv)，Python 里的 sys.argv）看到的只有它：没有引号，没有空格的信息，没有“这是一个通配符”的信息。从你敲下的那一行字到这个数组之间，是 bash 的展开。手册 Shell Expansions 一节有一段非常短的话，规定了它的顺序：

  1. 先把命令行切成词 (token)，引号在这一步生效：手册第一句就是“展开是在命令行被切成词之后进行的”。
  2. 花括号展开。
  3. 波浪线展开、参数和变量展开、算术展开、命令替换，这四个按从左到右的顺序一起做。进程替换（<(...)，第 5 篇）和它们同时发生。
  4. 分词。
  5. 路径名展开（通配符）。
  6. 去引号，永远是最后一步。

手册还有一句我觉得比顺序本身更重要：只有花括号展开、分词和路径名展开能让词的数量变多，其他展开都是一个词进、一个词出（例外只有 "$@"、$* 和数组的 "${name[@]}"）。换句话说，一行命令里“多出来的参数”只可能来自这三处，而分词和路径名展开恰好是对变量和命令替换的结果动手，也就是对你没有亲眼看过的文本动手。这一篇的全部内容大致就是：怎样让这两步只发生在你想让它发生的地方。

引用的作用只有一个：告诉 bash“这一段不要再动了”。它有四种写法，lab/ch02/quotes.sh 把它们并排放在一起（整个文件 24 行）：

  • 双引号只保留三样特殊：$（参数、算术、命令替换）、反引号和反斜杠，所以 ${name} 和 $((1 + 1)) 照常展开，结果是一个词 hello world 2。手册对反斜杠的规定很具体：它只在后面跟着 $、反引号、"、\ 或换行时才是转义，别的情况原样保留。实验里 "e\nf" 的输出是 e\nf，反斜杠和 n 都还在，而 "c\\d" 只剩一个反斜杠，就是这条规则。
  • $'...'（ANSI-C 引用，手册里的 ANSI-C Quoting 一节）像单引号一样不做展开，但会解释 \t、\n、\xHH 这类转义。要在 shell 里写一个换行或制表符，这是最干净的写法。

分词与 IFS#

命令替换和参数展开的结果，在没有引号包住的时候，会被切开。我习惯用快递分拣线来想它。argv 是一排包裹，每个包裹就是一个参数；引号是封箱的胶带，一个包裹贴了胶带就不会被拆；分词是传送带尽头的分拣机，它看到一个没有胶带的大箱子，就按 IFS 里的字符把它拆开。这个比喻我就用这一次，以后直接说分词。

lab/ch02/word_splitting.sh：

my notes.txt 没打引号变成两个词，加上引号是一个。这是最常见、也最容易被看出来的情形。我觉得真正让我停下来想的是第三个：空变量不打引号，参数直接消失，argc=0。手册把它说得很清楚：展开出来是空值的未加引号的参数叫“隐式空参数”，会被删掉；字面写出的 "" 或 '' 是“显式空参数”，会被保留。所以 "${empty}" 给你一个 <>，${empty} 给你什么都没有。它也是下面 [ $x = y ] 报错的原因。

[ $x = y ] 里的 $x 消失以后，[ 收到的是 =、y 和一个 ]，只有两个操作数，它理解成“= 是一个一元运算符”，报错，退出码 2。加上引号才是我们想要的：比较不相等，退出码 1。这也是 Google 指南偏爱 [[ ... ]] 的理由，[[ 里面不分词也不展开通配符。分词不是在每个地方都发生，手册给的范围是“参数展开、命令替换、算术展开的结果”，所以赋值、[[ ]]、case 这些地方天然是安全的：

IFS 是 Internal Field Separator 的缩写，它决定“在哪里切”。默认值是空格、制表符、换行（printf '%q\n' "$IFS" 在这台机器上打印 $' \t\n'）。实验里把它设成 : 以后，/usr/bin:/opt/my tools:/bin 被切成三个词，my tools 里的空格不再是分隔符；unset IFS 回到默认值，同样的变量就被空格切成了两个词，冒号反而不起作用。

最后一个实验是一个我很喜欢的写法：IFS=: read -r -a parts <<<"${path}"。变量赋值写在命令前面，只对这一条命令生效，所以不用事后手动恢复 IFS，不会忘记，也不会在中途出错的时候留下被改过的 IFS。read -a 把切出来的字段放进数组 parts，三个元素，每个元素里的空格都完好无损。（<<< 叫 here-string，第 5 篇细讲。）

手册里还有两句话值得抄下来：IFS 设成空串，就完全不分词（但隐式空参数仍然被删掉）；IFS 里如果有非空白字符，那么相邻的两个这样的分隔符之间会有一个空字段。后者我放到练习 4 里让你自己验证。

通配符的行为由几个 shopt 选项控制，lab/ch02/glob_options.sh 把它们逐个演示一遍。我挑出里面的各段：

  • 默认：没有匹配的模式保持原样，./*.nope 被原样传给程序 (argc=1)。这是通配符最阴险的地方：它在“有文件”和“没有文件”时给出完全不同形状的参数。
  • nullglob：没有匹配就展开成空，argc=0。循环 for f in ./*.log 在没有日志的时候就是零次迭代，这是我在脚本里要的行为。
  • failglob：没有匹配就报错，命令不执行：输出里没有 argc= 那一行，echo 'not reached' 也没有被执行（整个子 shell 被中止，状态 1）。报错在 stderr 里，运行器把它保存在 out/ch02/glob_options.stderr：.../lab/ch02/glob_options.sh: line 18: no match: ./*.nope。我把它放在子 shell 里，是因为它会让当前 shell 的这条命令失败，一个脚本里通常只想对某一小段开启它。
  • dotglob：* 默认不匹配以点开头的文件，所以 ./* 少了 .hidden。下一节 ls 少一个条目是同一个原因的另一种形式（ls 默认也不列点文件）。
  • globstar：默认 ** 只是两个 *，./**/*.txt 等于 ./*/*.txt，只找到下一层里的 sub/c.txt；打开 globstar 以后它才会递归，四个 .txt 都在。
  • extglob：!(a).txt 是“除 a 以外的任何名字加 .txt”，@(a|b).txt 是“a 或 b”。注意它必须在包含它的那一行被解析之前就打开，所以实验里的 shopt -s extglob 单独占一行。

这个实验的开头有一句 export LC_ALL=C：路径名展开的结果是排过序的，排序规则取决于 locale，我想让每个人跑出来的顺序一样。locale 第 6 篇再讲。

数组：保存 argv 的正确容器#

上面所有的“不打引号”都有一个共同的动机：我手里有一串东西（几个选项、几个路径），想把它们存起来，等会儿传给某个命令。把它们存成一个字符串，是最自然的想法，也是最常出错的想法。lab/ch02/arrays_argv.sh 把几种存法放在一起比较：

字符串版本有两个相反的失败，而且没有一个中间的写法能同时避开它们。不打引号：引号字符变成了数据，--exclude='*.tmp' 里的两个单引号被原样传给了程序（rsync 收到的模式带着两个引号字符，多半什么也排除不了），而目标目录 /tmp/my backups 被空格切成了两个词。打上引号：整串变成一个参数 argc=1，程序会把它当成一个叫“--exclude='*.tmp' --exclude=...”的选项。因为引号是 bash 读命令行时才处理的东西，它在变量赋值的那一刻已经用完了，存进字符串里的引号只是普通字符，没有人会再回头解释它。

数组没有这个问题：每个元素是一个独立的字符串，引号在赋值那一行被处理（所以 --exclude='*.tmp' 进数组以后是 --exclude=*.tmp，没有引号字符），"${flags[@]}" 把每个元素各自变成一个词，不分词，也不展开通配符。+=(...) 追加元素，可以按条件拼出一个选项列表，最后的 bash "${args}" "${opts[@]}" src/ "${dest}/" 得到 6 个正确的参数，--exclude 和它的值 a b 也保持是两个独立的词。

最后一对是空数组。"${opts[@]}" 和 "$@" 行为一致：没有元素就一个词也不产生 (argc=0)；"${opts[*]}" 像 "$*" 一样把所有元素拼成一个词，即使数组为空也是一个空串 (argc=1, <>)。我在 set -u 下试过空数组的 "${a[@]}"，在这台 5.3.15 上不会报“未绑定变量”，这个行为在更老的 bash 上不一样，我没有查是从哪个版本开始变的。

Google 指南关于数组的规定很简短，值得原文记住：用数组存列表，特别是命令行选项；用 "${array[@]}" 展开；别用字符串存序列，否则作者最终一定会去用 eval，或者试图在字符串里嵌套引号，“既不可靠，也不好读”。它还点名了一个反例：declare -a files=($(ls /directory))，先把 ls 的输出展开成一个字符串，再分词、再展开通配符，最后才变成列表。从命令输出填数组，用上一节的 mapfile -d '' -t arr < <(find ... -print0)。

Google 的引用规则，以及为什么是 "${var}"#

到这里，docs/code-style.md 里“展开与引用”那一条的每一个词我们都碰过了：

引用每一个展开；写 "${var}"，但 $1、$@、$?、$#、$$、$! 不加花括号（${10} 需要）。"$@" 传参数。参数列表放进数组，用 "${array[@]}" 展开。$(command)，不用反引号。

Google 指南的 Quoting 一节列出几条：含变量、命令替换、空格或元字符的字符串，总是加引号，除非你明确需要未加引号的展开；列表用数组；优先 "$@" 而不是 $*，原话是 Use "$@" unless you have a specific reason to use $*, such as simply appending the arguments to a string in a message or log.；$?、$#、$$、$! 这些 shell 内部的整数可以不加引号，但“命名的”内部变量，例如 PPID，最好加，求一致。

Variable expansion 一节规定了花括号：与已有风格一致，先于引号变量，其次才是偏爱 "${var}" 而不是 "$var"；单个字符的特殊参数和位置参数不加花括号。它还有一个提示框：花括号不是引用，双引号必须同时加。我花了一些时间想“为什么是 "${var}"”，试出来的理由有这几条。

统一。 "${var}" 永远成立，不用每次判断“这个变量后面会不会紧跟字母或下划线”。我找不出一个 "${var}" 比 "$var" 在引用安全性上更好的例子，所以它的价值不在保护，在不用动脑子。

不是引用。 花括号对 v='a b'; printf '<%s>\n' ${v} 没有任何帮助，仍然是两个词。${v} 只防边界，防不了分词。很容易写出满是 ${var} 却没有一对引号的脚本，看起来很规范，实际上一点保护也没有。

几件让我意外的事#

set -x 是一个引用调试器。 我原来把它当成“打印我执行了什么”的工具。实验里它真正好用的地方是：它打印的是 bash 重新加了引号之后的词，'x y' 和 x y 的区别直接告诉你一个词有没有被切开。接下来每次遇到“为什么这个命令收到的参数不对”，第一步我都会先开 set -x，而不是对着代码猜。

两起事故里没有一起是“忘了打引号”。 我写这一篇之前的印象是，这类事故的原因是不加引号。实际上我读了 Bumblebee 的全文和 Steam 的部分评论，再看 ShellCheck 的反应：Bumblebee 是字面文本里多了一个空格；Steam 那一行引号是对的，按评论者的推测是变量为空（这个原因我没有验证）。引号是必要的，但是不够，防御是三层：引号管分词，${var:?} 管空值，工具和审查管“你自己没看见”的那一行。我猜这也是为什么有经验的人写 rm 之前会有一个停顿。

探针本身也有盲点。 printf '<%s>\n' 对“零个参数”和“一个空参数”给出同样的输出，我是看着 <> 想了好几分钟才明白的。所以 args.sh 先打印 argc。我的猜测是，shell 里几乎每个“看起来对”的调试方法都有这样的盲点，这一点值得对每个新工具重新问一遍：它在什么情况下会把两种不同的情况显示成一样的？

写完这一篇，我对“shell 为什么这么设计”有一个并不确定的猜测：展开是为交互设计的。你在终端里敲 ls *.txt，希望它“就是能用”，没有人想在一次性命令里写 "$HOME"/"${dir}"/"${file}"。脚本继承了交互式的默认，却没有继承交互式的容错：你敲错了，立刻看到；脚本错了，可能是三个月后在别人的机器上，而且是 rm -rf。如果这个猜测对，那么整个系列里每一条 Google 规则，大概都是在把交互式的默认值一条一条换成脚本该有的默认值。

Tutorial用 Sift 重学 Python 第 25 篇：我在 Python 3.14.7、rustc 1.97.1 (2024 edition)、PyO3 0.30.1 和 maturin 1.14.1 上，把上一篇的分词扫描循环用 Rust 重写一遍，经 PyO3 变成 Python 模块 sift._rs，再接进 sift index --tokenizer rust。在 4.6 MB 的语料上（859485 个词元，3 轮交替测量取中位数），纯 Python（第 22 篇的版本）1435.6 毫秒，Rust 879.9 毫秒（1.62 倍），Cython 589.5 毫秒（2.43 倍），ctypes 和 cffi 是 1.28 倍和 1.32 倍；释放 GIL 并开线程的 Rust 版本是 1.51 倍，比串行版本还慢。Rust 的扫描本身只要约 28 毫秒，把结果变成 859485 个 Python 对象要花 280 到 550 毫秒，这个账 Rust 也还不掉。文中还有 Rust 错误与 panic 到 Python 异常的映射、Python::detach 的实测伸缩曲线、类型存根与 mypy.stubtest，以及全系列 25 篇的特性索引。

原生扩展（上）：C、ctypes、cffi、Cython 与 C API
Tutorial用 Sift 重学 Python 第 24 篇：我在 Python 3.14.7、gcc 15.3.0、Cython 3.2.5 和 cffi 2.1.0 上，把 Sift 分词的扫描循环用 C 重写一遍，再分别用 ctypes、cffi、Cython 和手写的 C API 模块接回 Python。我本以为 C 会快一个数量级，结果在 4.6 MB 的语料上（859485 个词元，3 轮交替测量取中位数），纯 Python 664.2 毫秒，ctypes 727.6 毫秒（0.91 倍），cffi 688.0 毫秒（0.97 倍），只有 Cython 到了 342.0 毫秒（1.94 倍）：C 函数本身只要 15.3 毫秒，时间都花在为 859485 个词元造 Python 对象上。数 CJK 字符这种几乎不造对象的活，C API 模块 1.0 毫秒，比 Python 的 38.2 毫秒快约 38 倍。一次调用的固定开销从 34 纳秒（空函数）到 702 纳秒 (ctypes)，决定了多短的字符串不值得过边界。中途我还让 ctypes 段错误一次，看 faulthandler 怎么说，用 hypothesis 重现了一类偏移映射的 bug，并确认四种实现建出的 segment.sft 逐字节相同。

性能：剖析、字节码特化与优化
Tutorial用 Sift 重学 Python 第 23 篇：我在 Python 3.14.7 上用 timeit、cProfile、pyinstrument、py-spy、memray、tracemalloc 和 sys.monitoring 把 sift index --full 与 sift bench search 量了一遍，再动手改。原先我猜慢在 BM25 循环，剖析器说不是：12 个查询在 cProfile 下共 1.862 秒，其中 1.834 秒是生成片段，打分加排序只有约 28 毫秒。改了六处热点，先用一个钉住 12 个查询前 10 名的测试，再优化；5 轮交替测量，12 个查询从 1005.7 毫秒降到 525.1 毫秒（1.92 倍），索引构建内部计时从 3070.1 毫秒降到 2621.0 毫秒（1.17 倍），segment.sft 与 ch22 逐字节相同。中途量到：str.translate 在 ASCII 文本上比 21 次 replace 快 4 倍，在含 emoji 的语料上反而慢 1.5 倍；3.14 的 BINARY_OP 在第二次执行时特化，换成另一种类型后第 53 次才重新特化；这台机器的 Python 没有 JIT，也不是尾调用解释器；kernprof 不在开发环境里，我用 sys.monitoring 的 LINE 事件自己做了一个逐行计数器。
