上一篇结尾我们手写了三个 impl Spanned，一共 44 行，每个分支都在做同一件事：把叫 span 的字段取出来。我给 Stmt 加一个变体，编译器老老实实指出三处要改，其中一处纯属体力活。C++ 程序员遇到这种事有两条路：写一个宏，或者让代码生成器生成。Rust 给了第三条路：写一个在编译器内部运行的 Rust 函数，输入是你的类型定义，输出是要补进程序里的代码。这一篇我们写出这个函数，然后把那 44 行删掉。

本篇检查点

你将写出 pebble-macros 的中间版本（只有 #[derive(Spanned)] 这一个宏，约 100 行），然后回到 pebble-ast：加一行依赖、一行 pub use、三处 #[derive(.., Spanned)]，删掉三个手写的 impl。做完以后 pebble-ast 与仓库逐字节相同，cargo test -p pebble-ast 的 4 个测试一个字不改。用到的 Rust 特性：proc-macro = true 的 crate、TokenStream、syn、quote!、泛型的 split_for_impl、绝对路径与卫生性、syn::Error、collect 成 Result。 上一篇是 递归类型、泛型与 trait：搭一棵 AST，这一篇从它的中间版本继续。下一篇是 Result、? 与递归下降。

宏有几种#

我先给 C 程序员一个参照。C 的 #define 是文本替换：

预处理器不知道 x 是什么，括号加得不对就产生奇怪的结果，也永远不知道 span 是不是真的存在。Rust 的宏不一样：它们工作在 token 树上，括号永远配对，替换的单位是”一个表达式”而不是”几个字符”。而且 Rust 有四种宏：

种类写法谁写、在哪里本系列在哪讲
声明宏macro_rules! name { ... }模式匹配 token，同一个 crate 里就能写第 10 篇（chunk!）
derive 宏#[derive(Name)]过程宏：给一个类型生成额外的 impl这一篇
函数式过程宏name!(...)过程宏：输入 token，输出任意 item第 10 篇（opcode_set!）
属性宏#[name]过程宏：整个 item 进、整个 item 出第 12 篇（#[differential]）

你已经天天在用其中三种了：println! 是（声明）宏，#[derive(Debug)] 是 derive 宏，#[test] 是属性宏。它们没什么神秘的，只是别人写好的 Rust 函数。过程宏就是这样一个函数，签名大概是”一串 token 进，一串 token 出”，编译器在展开时调用它。

打个比方：过程宏像 C 工程里的 protoc 或 flex/bison：构建过程中先跑一个程序，它读你的声明，吐出一些源文件，再被编译。区别在于，它不是一个外部命令加一个 Makefile 规则，而是 cargo build 自动在编译器进程内调用的一个动态库，输入输出是 token，不是文本。

为什么必须是单独的 crate#

过程宏必须放在一个 proc-macro = true 的 crate 里。为什么不能直接写在 pebble-ast 里？因为编译 pebble-ast 的时候，编译器要运行宏：宏得先被编译成可以加载的库。同一个 crate 不可能先于自己编译完成，所以必须拆成两个 crate，先编译宏的那个。

为什么有两种 TokenStream#

刚才的 .into() 要回答一个问题：为什么有 proc_macro::TokenStream 和 proc_macro2::TokenStream 两种？

proc_macro 是编译器内置的，只有宏被编译器调用的时候才能用（刚才的 E0433 实验只是最直观的一面：普通 crate 里根本找不到它）。我的理解是，这让依赖它的代码很难测试，也很难在宏之外复用；syn 和 quote 如果直接依赖它，它们自己就没法写测试了。proc-macro2 是一个普通 crate，提供一个同样形状的 TokenStream，在宏里和 proc_macro 的那个来回转换（.into()），在宏外面也能跑。我的实验文件 ch06_proc_macro2_outside.rs：

所以约定很简单：入口函数的签名用 proc_macro::TokenStream，里面的所有函数都用 proc_macro2::TokenStream。你在后面的代码里会看到 use proc_macro2::TokenStream as TokenStream2;，2 就是这个意思。

[macro@Spanned] 是文档链接的消歧义写法：这个名字既可能指 trait 也可能指宏，macro@ 前缀说是宏。（这个名字冲突的问题稍后专门讲。）

入口函数薄薄一层，真正的逻辑放进一个普通函数，签名里用 TokenStream2：

这里没有直接 quote! 返回，因为生成过程可能失败：用户可能把 derive 用在没有 span 字段的类型上。expand_spanned 返回 syn::Result<TokenStream2>，也就是 Result<TokenStream2, syn::Error>。出错时调用 error.to_compile_error()：它生成的 token 是一个 compile_error!("...") 调用，位置落在你指定的 token 上。编译器展开后看到它就报错。这个设计让宏永远不 panic：错误是返回值，位置是精确的。Result 和 ? 到第 7 篇才系统讲，这里先当成”可能是 Ok(值) 也可能是 Err(错误)，用 match 分开处理”。

expand_spanned：结构体#

input.data 是 Data 枚举：Struct、Enum、Union 三种，对应 Rust 的三种自定义类型。match &input.data 对它做穷尽匹配（第 3 篇的老朋友），所以 union 也得处理。结构体分支把字段名取出来，生成 self.span。body 是一小段 TokenStream2，最后被插进 impl 里。

span_member：找到叫 span 的字段#

这是整个宏里 Rust 味最浓的一段，我一层层剥：

  • Fields 也是枚举：Named（{ a: T }）、Unnamed（(T, U)）、Unit（没有字段）。Pebble 的所有 AST 节点用具名字段，所以只接受 Named，其余用 _ => 兜底并返回错误。
  • named.named 是字段的有序列表：外层的 named 是 Fields::Named 里装的那个结构（FieldsNamed），里面的 named 才是字段的集合，名字撞了，不是笔误。.iter().find(...) 找第一个满足条件的字段，返回 Option<&Field>。
  • field.ident 是 Option<Ident>（具名字段一定是 Some，但类型对元组字段也通用）。.as_ref() 把 &Option<Ident> 变成 Option<&Ident>，.is_some_and(|id| id == "span") 在有名字时比较它是否等于 "span"。syn::Ident 可以直接和字符串比较，这是它实现的 PartialEq。
  • .and_then(|field| field.ident.clone())：找到了字段，就把它的名字克隆出来；没找到（None）还是 None。
  • .ok_or_else(|| ...)：Option 到 Result 的桥：Some(x) 变 Ok(x)，None 变 Err(闭包的返回值)。闭包只在 None 时才被调用，所以不会白白构造错误。
  • syn::Error::new_spanned(fields, "...")：创建一个错误，位置取自第一个参数的 token。这是自定义编译错误的关键：位置指向用户的代码，而不是宏的代码。

这里有一件让人疑惑的事：同一个文件里有两行 pub use ...::Spanned，名字一样，不冲突吗？Rust 的名字分属三个命名空间：类型（包括 trait）、值（函数、常量）、宏。pebble_span::Spanned 是 trait，在类型命名空间里；pebble_macros::Spanned 是 derive 宏，在宏命名空间里。两个 use 各占一个，互不干扰。#[derive(Spanned)] 在宏的命名空间里找，impl Spanned for X 在类型的命名空间里找。标准库的 #[derive(Debug)] 和 trait Debug 也是这样同名的。

值不值#

诚实地算一笔账。

  • 代码行数：删掉 44 行手写代码，新增一个 70 行（不含注释和空行）的宏 crate。就这个项目的规模，光看行数是亏的。
  • 编译时间：我在一个全新的 target 目录里各编译一次 pebble-ast。没有宏的版本，0.45 秒；有宏的版本，4.56 秒（proc-macro2、quote、unicode-ident、syn 和 pebble-macros 都要先编译一遍）。大约 10 倍，单次测量，机器有 16 核，只能当个量级。不过它们是外部依赖，只在干净构建时付一次，增量编译里不会重复。

2. 为什么过程宏不能”找类型是 Span 的字段”？ 你写一个宏，想让它在字段 range: Span 上也工作，办法是比较字段的类型。这为什么靠不住？

参考答案

宏拿到的只是 token：字段类型在它眼里是一个标识符 Span。它不知道那个 Span 是 pebble_span::Span、std::ops::Range 的别名，还是用户自己定义的另一个类型。用户也可以写 use pebble_span::Span as Loc;，那时类型的 token 是 Loc；或者写成 pebble_span::Span，token 是三段路径。宏要做的比较在名字解析（以及类型别名展开）之前，没有可靠的办法。

上面 ch06_wrong_type.rs 是对称的证据：字段名叫 span 但类型是 u32，宏毫无察觉，一直到类型检查阶段才被拒绝。要让宏看见类型信息，必须由用户在宏参数里明确说出来，所以辅助属性（练习 1）是惯用做法。
