raw 到第三个包就烦了#

回头看 mini/raw.nix，它只有 12 行：一个名字，一段脚本，builder 是 busybox 的 sh，PATH 是 busybox 的 bin。每个包都要自己做这几件事：

  • 把依赖的 bin 目录接到 PATH 上；
  • mkdir -p "$out"，因为 Nix 只告诉你输出路径，不替你建；
  • 如果有源码，解开它并 cd 进去；
  • 装完之后把脚本里的解释器路径改成 store 里的绝对路径。

这四件事和具体的包无关。把它们放进一份所有包共用的脚本，每个包只剩下“我的源码是什么、我的构建命令是什么、我的安装命令是什么”，这就是 stdenv 在做的事。这里值得停一下，想想“每个包只剩下差异”在 Nix 里怎么实现：差异只能通过 derivation 的属性传进去，而属性在构建时只有一种形态，就是环境变量。Nix 手册在derivation 一章里写得很明白：除了 name、system、builder、args、outputs 这些有特殊含义的，“Every other attribute is passed as an environment variable to the builder”，字符串原样传，store 路径展开成路径，列表用空格连起来，true 是 1，false 和 null 是空字符串（源文件 doc/manual/source/language/derivations.md 的 213 到 235 行）。

所以 stdenv 的骨架就是：包的差异是一组环境变量，builder 是共用的脚本，脚本按约定的名字(buildPhase、installPhase)去读这些变量。接下来我就这么写。

mkDerivation：29 行#

mini/stdenv/default.nix 整个文件：

逐段看。参数是一个带 ... 的 pattern，再用 @args 绑定整个 attrset（第 3 篇的内容）。name 必须有，其余有默认值。... 让包可以传任意额外的属性，它们会原样进 removeAttrs args [ "src" ] 然后进 derivation，也就是进环境变量。greeting 包里的 text 就是这么到达 setup.sh 的，下面会看到。

src 单独处理：只有非 null 才加进 derivation。按手册的规则，null 会变成空字符串的环境变量，那样 .drv 里会多一个空的 src；不传，.drv 里就干净。setup.sh 里对应的判断是 [ -n "${src:-}" ]。

builder = "${busybox}/bin/sh" 和 args = [ ./setup.sh ] 是整件事的核心：所有包的 builder 是同一个 shell，同一个脚本。./setup.sh 是个路径字面量，求值时被复制进 store，成为每个包的输入源文件。inherit ... busybox 让 busybox 的 store 路径作为环境变量 busybox 传给脚本，同时（字符串上下文，第 4 篇）把它登记成输入依赖。

mini 和 nixpkgs 的 mkDerivation 在这里的差别我先记一笔：nixpkgs 的参数是 pname 加 version，system 取自 buildPlatform，builder 是 stdenv 里那个 bash。结构一样：把包的属性变成 derivation 属性，再附上 builder 和 args。后面读 make-derivation.nix 时能看到对应的行。

setup.sh：63 行#

mini/stdenv/setup.sh 是 POSIX sh，由 busybox 的 sh 执行。我只引用要紧的部分。开头设 PATH：

${buildInputs} 在这里已经是 Nix 传进来的环境变量，是用空格连起来的 store 路径列表（手册规则里“列表用空格连起来”），所以 for dep in ${buildInputs} 不加引号，按空格拆开。这就是 nixpkgs 里那一大套依赖处理在 mini 里的全部：一个循环，把每个依赖的 bin 放到 PATH 最前面。

然后是整个脚本的发动机，run_phase 和主循环：

每个阶段先打印一行 == phase <name>，然后三选一：环境变量 <name>Phase 存在就执行它；否则 unpack 在有 src 时走默认实现；fixup 总是走默认实现；patch、build、install 没有默认，什么也不做。

为什么用 printenv "$1Phase"？阶段名是运行时拼出来的（buildPhase 这个变量名由 $1 加 Phase 拼成），要按名字取变量的值，需要“间接展开”。bash 有 ${!name}，但这是 bash 的扩展，POSIX 没有定义，而 mini 的 setup.sh 要在 busybox 的 sh 下跑，所以我借 printenv 绕过去：让一个外部程序按名字取环境变量。nixpkgs 的 setup.sh 是 bash，直接写 eval "${!curPhase:-$curPhase}"，后面会看到那一行。

写成文件再用 . 载入而不是在子 shell 里跑，是因为我要阶段之间共享当前目录：unpack 阶段 cd 进源码目录，后面的 build、install 都在那里执行。. 在当前 shell 里执行文件，所以 cd 持续有效（对照：Cairn 第 1 篇练习 4 里 source 和 bash ./f 的区别，同一个道理）。set -eu 因此也对阶段里的每一行生效：任何一条命令失败，整个构建失败。

默认的 unpack 和 fixup：

src 如果是目录（比如 site 的 ./site），就复制过来再 chmod -R u+w，因为 store 里的东西是只读的，复制之后权限位还在，不加写权限后面没法改。如果是文件就 tar xf，并且在压缩包只有一个顶层目录时进去，GitHub 的源码包就是这个形状。default_fixup 只做一件事，把 $out/bin 里每个脚本第一行的 #!/bin/sh 或 #!/usr/bin/env sh 换成 #!${busybox}/bin/sh，是 nixpkgs 里 patchShebangs 的一个极小的替身。

依赖的分类：偏移量#

前面我一直在说“构建时依赖”和“运行时依赖”。nixpkgs 把这两个词换成了一套更精细的说法，因为它要同时支持交叉编译：同一个包可能要在一台机器上构建、在另一台机器上运行，还可能是一个为第三台机器生成代码的编译器。

Nixpkgs 手册的交叉编译一章定义了三个平台：build 是构建这个包的机器，host 是这个包将要运行的机器，target 只对编译器之类产出机器码的工具有意义，是它产出的代码要运行的机器。依赖被分成几类，由两个数决定：依赖自己在哪个平台上运行（host 偏移），以及它（如果是编译器）为哪个平台产出代码（target 偏移）。偏移量是相对于正在构建的包的：setup.sh 的 696 到 697 行定义了它们：

mini 的每个包只有一个输出 out。nixpkgs 的包经常有好几个，lab/ch07/multiple_outputs.sh 看锁定版 zlib 的：

zlib 的 outputs 是 [ "out" "dev" "static" ]，在 default.nix 的 64 到 68 行里写着 outputs = [ "out" "dev" ] ++ lib.optional splitStaticOutput "static"。三个输出是三个独立的 store 路径：运行时的共享库在 out（自己 132,608 字节），头文件和 .pc 在 dev（122,832 字节），静态库 libz.a 在 static。out 的闭包 37,850,496 字节，大头是 glibc；dev 的闭包 38,126,240 字节，比 out 多 275,744 字节，是 dev 自己的 122,832 加上 static 的大小（实验没有单独打印 static，这一项是推断）。差别是 0.7%，数字小，但意义是方向：一个只要运行 zlib 的包，闭包里不需要头文件和静态库；dev 引用 out（上面的 references），反过来不引用，所以放 out 不会拖进 dev。

机制分三层。Nix 这一层，outputs 列表里每个名字变成一个环境变量，值是对应的 store 路径，builder 往这些路径里分别写文件（Nix 手册 derivation 一章，doc/manual/source/language/derivations.md 136 行：“Each output name is passed to the builder executable as an environment variable”）。nixpkgs 这一层，multiple-outputs.sh 这个 hook（也在上面那 14 个默认 hook 里）在 preConfigureHooks 里注册 _multioutConfig，自动给 configure 加上 --includedir="${!outputInclude}"/include、--libdir="${!outputLib}"/lib 这样的参数（66 到 96 行），把文件放进对的输出。zlib 的 configure 不是 autoconf，所以它设了 setOutputFlags = false（第 69 行）自己传 --includedir=${placeholder "dev"}/include（79 到 81 行）。依赖这一层，手册的多输出一章写：一个多输出的包放进别人的 buildInputs 时，“the dev output is added if it exists, otherwise the first output is added”。这就是上一节的 PKG_CONFIG_PATH 里是 ...-zlib-1.3.2-dev/share/pkgconfig 而不是 zlib-1.3.2 的原因：pkgs.zlib 放进 packages，取到的是它的 dev，dev 的 .pc 文件再指回 static 的 -L 和 out 的 -L（上一节 pkg-config --libs 输出里的两个 -L）。

引导：这个 stdenv 本身是谁编译的#

读到这里有一个问题在我脑子里转了很久：stdenv 里有 gcc，gcc 要用 C 编译器编译，那第一个 C 编译器是哪来的？

bootstrappable.org 的首页开头是个类比：“Do you know how to make yoghurt? The first step is to add yoghurt to milk! How can you build a compiler like GCC? The first step is to get a compiler that can compile the compiler.” 它接着说，用户和发行版因此依赖不透明的预编译二进制，“our goal is to minimize the amount of bootstrap binaries.”(bootstrappable.org)这个类比我只用这一次：酸奶要靠上一罐酸奶，编译器要靠上一个编译器。一路追到头，总得有一个东西不是从“上一个”来的。Ken Thompson 的图灵奖演讲《Reflections on Trusting Trust》说的就是这一路上藏东西有多容易，bootstrappable.org 把它列在延伸阅读里。

跑 6 个：unpack、patch、configure、build、install、fixup。跳过 3 个：check、installCheck、dist。依据是 runPhase 的 1745 到 1753 行：前面的六个只在对应的 dont* 变量非空时才 return，默认没人设，就会跑；checkPhase、installCheckPhase、distPhase 要 doCheck、doInstallCheck、doDist 非空才跑，默认不设，就跳过。（doCheck 的默认值在 make-derivation.nix 里是 doCheckByDefault，所以这是 setup.sh 层面的答案，具体的包可能设了 doCheck = true。）

3. 为什么 mini 的 hello 闭包里有 greeting，而 site 的闭包里没有 hello？

参考答案

引用扫描只看输出的内容。hello 的 installPhase 用 ${greeting} 把路径写进了输出里的脚本，所以 greeting 在它的闭包里（mini_build.stdout：3 个路径，1,496,288 字节）；site 的输出只有一个 HTML 文件，里面没有任何 store 路径，闭包只有它自己（544 字节），尽管它构建时用了 hello（mini_drv_env.stdout 里 hello 的 buildInputs 是空串，而 site.nix 的 buildInputs 里有 hello 和 wordfreq）。buildInputs 决定构建时能用什么，引用扫描决定运行时依赖什么，两个是独立的集合。

4. findInputs 的开头有一行 (( hostOffset <= targetOffset )) || exit 1。这对 -1 0 1 三个偏移意味着哪几个组合不存在？

参考答案

偏移是 (host, target)，要求 host 不大于 target。9 个组合里合法的是 (-1,-1)、(-1,0)、(-1,1)、(0,0)、(0,1)、(1,1) 六个，恰好对应 808 到 825 行的六个循环；不合法的是 (0,-1)、(1,-1)、(1,0) 三个，也就是依赖的 host 比 target 更“晚”。手册的说法是 “we prohibit dependencies from a “later” platform to an earlier platform to limit confusion because we’ve never seen a legitimate use for them”（交叉编译一章，doc/stdenv/cross-compilation.chapter.md）。所以没有 depsHostBuild 之类的名字，也不需要。

5. 按 bootstrap_seed.sh 的输出，572 个 .drv 里固定输出占多大比例？bootstrap-stage0-stdenv-linux 的闭包占多大比例？

参考答案

固定输出 137 个，137 除以 572 约等于 23.95%，也就是将近四分之一的 .drv 是“从外面下载一个东西”（源码包、补丁、种子）。stage0 的闭包 307 个，307 除以 572 约等于 53.67%。这两个集合有很大的重叠：stage0 里的很多名字是 .tar.gz、.tar.xz、.patch（见上面列表），都是固定输出。我没有算两个集合的精确交集。

下一篇#

这一篇我们造了一个包集，它的所有东西都在 legacyPackages.<system>.mini 下面，而 flake.nix 里为它加的几行是我手写的、没有整理过的：miniFor 在每个系统上各建一份，checks 和 legacyPackages 各自 forAllSystems。下一篇，第 8 篇《flake：inputs、outputs、flake.lock 与纯求值》，我们把 flake.nix 从头读一遍：inputs 和 outputs 是什么，flake.lock 里记了什么，为什么一个没被 git add 的文件在 flake 里会“不存在”，nix eval 在纯求值模式下为什么不让你碰 builtins.currentSystem，以及这个“实验性”的功能为什么五年来一直是我日常的地基。到那时，你会看到这篇里那一行 legacyPackages.<system>.mini 在 nix flake show 里是什么样子。
