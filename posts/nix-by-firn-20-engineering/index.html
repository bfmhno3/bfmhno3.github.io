第 6 篇我写过：store 路径里的哈希是输入的指纹，只要输入一样，路径就一样。这条规则留下了两个我一直没量过的问题。第一，“输入一样”不等于“输出一样”：第二次构建得到的是不是同样的字节，Nix 自己并不保证。第二，同一个路径在任何一台机器上都指向同一个东西，那我在一个空 store 里构建 firn-hello（一个很小的 C 程序）为什么有时要等将近四分钟？这一篇把这两个问题都量一遍，然后把 Firn 的全部检查搬到 GitHub Actions 上，最后给这个系列做一张索引。

KVM：给 /dev/kvm 放权限#

三个虚拟机测试需要 /dev/kvm。workflow 的 L27 到 L31：

这三行不是我发明的，它们和 GitHub 在 2024-04-02 的更新日志里给 Android 模拟器写的那一段一模一样（GitHub Changelog，当时的说明是 2 vCPU 的 Linux runner 也能用硬件加速了）。意思是：写一条 udev 规则，让内核设备 kvm 的组是 kvm、权限是 0666；按 udev(7) 的说法，static_node=kvm 是把规则里的权限应用到 systemd-tmpfiles 在 udevd 启动之前创建的静态节点上，规则本身不创建节点；然后重载规则并对 kvm 设备触发一次。0666 的代价是任何用户都能打开 /dev/kvm，在一台只存活几十分钟、只有我的代码的虚拟机上这没关系，在共享的自托管 runner 上就是另一回事了。

两个安装器#

L33 到 L39：

同一个 job 里两个互斥的步骤，用 if: 选一个。前者是 Cachix 维护的 install-nix-action，README (2026-11-08 查) 的卖点是安装快（“~4s on Linux”）、在 Linux 上默认多用户安装并开沙箱；后者是第 19 篇见过的 Determinate 一家：determinate-nix-action 基于 Determinate Nix Installer，README 里默认装的版本是 v3.24.2 (2026-11-08 查)，和我在第 19 篇的虚拟机里量的是同一个。

它们有一处相同，而这一处恰好是“substituters、trusted-substituters 和 trusted-users”一节的实际场景：install-nix-action 默认 set_as_trusted_user: true，determinate-nix-action 默认 trust-runner-user: true，都会把 runner 用户放进 trusted-users。没有这一步，下一步的 cachix-action 就没有权限往 Nix 里加一个新的 substituter：这是我从手册的 trusted-users 条目推出来的，我没有在 runner 上验证。

Cachix：先拉，后推#

L41 到 L46：

cachix-action 的 README (2026-11-08 查) 一句话说完了它的工作：“After each job, newly built packages are pushed to your binary cache.” README 里在它之前还有一句：“Before each job, packages to be built are first downloaded (if they exist) from your binary cache.” 推送默认走守护进程模式：它给 Nix 注册一个 post-build-hook，每个新构建出来的路径立刻被推走；README 同时写了限制，“Nix does not trigger the hook for substituted paths”，也就是说从 cache.nixos.org 拿来的路径不会被推。我猜这意味着 bfmhno3-firn 里装的主要是 Firn 自己构建的东西；pebble 确实在里面（见本节 cachix_hit_host.sh 的输出），别的包我没有逐个查。

authToken 来自仓库 secret CACHIX_AUTH_TOKEN。gh secret list -R bfmhno3/firn 只列名字，它在列表里；令牌本身我没碰过，也不会出现在任何一篇文章里。README 的安全一节有三句我觉得应该原样记住：“Cachix tokens and signing keys provide full read and/or write access to your caches.” “GitHub Actions allows anyone who can edit workflow files to read secrets.” “Forked pull requests cannot access secrets, so they can only read from public caches.” 一个能改 workflow 的人能读到令牌，这就是为什么写权限只该给你信任的人。

二进制缓存：一个目录加几个文件#

Nix 的二进制缓存没有任何魔法，它是一个 HTTP 服务器（或者一个目录）上的三类文件：nix-cache-info 描述这个缓存本身，每个 store 路径一个 <32 位哈希>.narinfo 描述这个路径，nar/ 目录里是路径内容的归档 (NAR)，通常压缩过。Nix 要找一个路径，就拿它的哈希部分去请求 <hash>.narinfo，有就读，没有 (404) 就问下一个缓存。我把它比作图书馆之间的馆际互借：narinfo 是馆藏卡片，写着书名、页数和它引用了哪些别的书；NAR 是书本身；签名是馆长在卡片上盖的章，我只借我认得章的馆里的书。这个比喻我就用这一次，接着回到文件。

substituters、trusted-substituters 和 trusted-users#

信任有两层，容易混。一层是“这个缓存的东西我信不信”，由 trusted-public-keys 决定，“签名签的是什么”一节已经演示了。另一层是“谁有权让守护进程去问这个缓存”，由 substituters、trusted-substituters 和 trusted-users 决定。手册对 substituters 的说法是，要使用一个缓存，至少满足两个条件之一：它在 trusted-substituters 里，或者调用 Nix 的用户在 trusted-users 里；除此之外每个 store 路径还要按 trusted-public-keys 受信任。trusted-substituters 是给普通用户的白名单：只在 allowed-users 里、不在 trusted-users 里的用户，只能在 substituters 里放它列出的那些地址。

Cachix：推、令牌和公钥#

镜像只能拉官方缓存里已经有的东西。Firn 自己构建出来的东西（pebble 在第 11 篇冷构建要 253.4 秒），想让 CI 和读者都不重新构建，就得有一个自己的缓存。我用的是 Cachix。它的文档把流程讲成三步。第一步，登录 Cachix 网站，创建一个缓存（名字会出现在 Nix 配置里，“visible to anyone using it”）；第二步，认证，令牌有两种：个人的（“full access to your account”）和 per-cache 的（只对某一个缓存有读或写权限），可以用 cachix authtoken 或环境变量 CACHIX_AUTH_TOKEN 设置；第三步，推，nix-build | cachix push mycache，或者在 CI 里用 cachix-action。读的一边是 cachix use mycache，它会改 Nix 的配置。

第 1 篇起，每个 Nix 块我都说“nixfmt --check 不打印任何东西”，却没有说过 nixfmt 从哪里来。来历有出处可查。NixOS/rfcs 的 RFC 166 “Nix formatting, take two” 由 piegames 在 2023-11-15 开出，PR 的描述说它是 RFC 101 的继任者，要做五件事：定义最初的“标准 Nix 格式”，成立 Nix formatter 小组，创建官方格式化工具，用它重排 Nixpkgs，并要求 Nix CLI 里任何默认的格式化都必须用官方的这个。RFC 的动机一节写得很实在：“People should not be bothered with formatting.” “We want to prevent future debate around how things should be formatted.” 它在设计上的取舍也坦白：“Bad code does not deserve good formatting.” PR 带着 status: accepted 的标签，最后一轮 FCP 的号召写着收尾会议在 2024-03-04，2024-03-05 的评论里已经有人在祝贺。

落地花了更久：Nixpkgs 在 2025-04-01 被整个重排，Discourse 上的公告写的是 “everything went according to plan, Nixpkgs is fully formatted”（公告；PR 是 NixOS/nixpkgs#380990）；nixfmt 的 v1.0.0 在 2025-07-14 发布，发布说明称它是 “the first stable release of the official Nix formatter”，基础就是 RFC 166，并说格式变得“unrecognisable from previous versions”。这台机器上的 nixfmt 是 1.4.0，已经是那条线上的后来版本。

在 Firn 里它出现在三处：Makefile 的 lint 目标第一行 nixfmt --check $(NIX_FILES) (L19)；nix fmt，第 8 篇给 flake 配的 formatter 是 nixfmt-tree；以及“两个入口：make lint 和 flake check”一节的 lint 检查。nixfmt-tree 是 nixpkgs 里的包，nixfmt 的 README 说它是预先配好 nixfmt 的 treefmt，因为 nixfmt 本身一次只处理一个文件。

  • Nix 2.34 参考手册：每一个 nix 子命令和每一项设置的出处。这一篇引用的 trusted-users、require-sigs、accept-flake-config 都在它的 nix.conf 一页里。
  • Nixpkgs 手册和 NixOS 手册：第 10 到 14 篇是 Nixpkgs 手册的入口，第 15 到 17 篇是 NixOS 手册的入口。
  • nix.dev：官方的教程和概念文章，按主题而不是按命令组织。
  • 读 Nix 的源码：这一篇我读了 path-info.cc、local-store.cc、derivation-builder.cc 和 libflake/config.cc 四处，办法是从一条错误消息 grep 回去。挑一条你经常看到的错误试试。
  • NixOS/rfcs：RFC 166 的来龙去脉是这样读到的；要知道一个东西为什么长成现在这样，通常有一个 RFC 或一个很长的 PR 讨论。
  • 把 Firn 的 ci.yml 抄进你自己的仓库，把 make ci 换成你自己的检查，然后看第一次冷缓存和第二次热缓存差多少。
