一点历史：RFC 49、Nix 2.4 和“实验性”#

先把历史说清楚，因为这个功能的“实验性”会在后面反复出现。

flake 最早的正式提案是 RFC 49，标题是 “[RFC 0049] Flakes”。它的摘要是一句分了三段的话，正好是后面每一节的主题：“Flakes allow hermetic, reproducible evaluation of multi-repository Nix projects; impose a discoverable, standard structure on Nix projects; and replace previous mechanisms such as Nix channels and the Nix search path.” 拆开就是三件事：

  • 可复现的依赖（钉死版本）：flake.lock 那几节；
  • 封闭的求值 (hermetic evaluation)：纯求值那一节；
  • 标准的结构：输出的 schema 那几节。

这个 PR 在 GitHub 上现在的状态是 closed，没有合并；我没有去考证它为什么这样收场，也不打算猜。我能确认的是，nixpkgs 自己的 flake.nix 在锁定的提交上还保留着对它的引用：第 1 到 2 行写着 # Experimental flake interface to Nixpkgs. 和 # See https://github.com/NixOS/rfcs/pull/49 for details.。

flake 真正进入 Nix 是在 2.4。Nix 手册里的 2.4 发布说明（发布日期 2021-11-01）写道：“Flakes are currently marked as experimental.” 第 1 篇的历史表里已经有这一行。到了 2.34.9，实验性功能一页里仍然列着 flakes (“Enable flakes. See the manual entry for nix flake for details.”)，nix flake 的手册页顶上也还挂着“experimental, interface subject to change”的警告（那条警告链接的是 nix-command 这个实验性功能）。所以截至这一篇的 Nix 版本，flake 在上游手册里的身份是：自 2.4 起，整整五年，仍是实验性功能。第 1 篇里我提到的 /etc/nix/nix.conf，就靠 experimental-features = nix-command flakes 这一行才让本系列的每条命令能跑起来。

这个别扭，一个“实验性”的东西同时是我的日常，我会留到后面“我对 flake 不满意的三件事”一节再展开。先把它拆开。

flake.nix 的四块#

一个 flake 就是一棵目录树，根目录有 flake.nix。手册列的属性有四个：description、inputs、outputs、nixConfig。Firn 的 flake.nix 开头是这样的：

description 是一行说明，nix flake metadata 会打印它。inputs 是依赖，一个属性集：名字对应 flakeref（下面有一节专门讲），inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable" 的意思是“我依赖 GitHub 上 NixOS/nixpkgs 仓库的 nixos-unstable 分支”。注意这时候还没有版本：分支是会动的。把它变成确定的提交，是 flake.lock 的事。

outputs 是一个函数。手册的说法是：它接受一个属性集，里面是每个输入的输出，键是输入的名字，返回这个 flake 提供的值。Firn 里写的 { nixpkgs, ... }: 就是从这个属性集里取出 nixpkgs；... 吃掉其他的（比如 self，下一节）。

这个 nixpkgs 是什么？是 nixpkgs 那个 flake 的输出，加上几个元数据。所以 nixpkgs.lib 是 nixpkgs 的 outputs 返回的 lib，nixpkgs.legacyPackages.${system} 是它返回的 legacyPackages 在某个系统上的那一份，也就是我们前几章一直在用的整个 nixpkgs。它同时还带着 outPath（源码树在 store 里的路径），手册的说法是，这样这个属性集可以像路径一样传给 import，import nixpkgs { ... } 这种写法就是这么成立的。

最后一个 nixConfig，是一组 nix.conf 选项，评估这个 flake 时生效。因为涉及信任，放到后面的小节，和第 20 篇的 CI 一起讲。

Firn 的 nixpkgs.lib.genAttrs systems 是整篇里最“样板”的一行。genAttrs 的文档例子在 nixpkgs 里：lib/attrsets.nix 的 1344 到 1347 行，genAttrs [ "foo" "bar" ] (name: "x_" + name) 得到 { foo = "x_foo"; bar = "x_bar"; }。所以 forAllSystems f 就是“对 systems 里的每个名字调用 f，把结果放进以名字为键的属性集”。为什么每个输出都要按系统展开一遍，会在“纯求值”那一节有答案。

outputs 的约定：一张表#

outputs 返回的是一个任意的属性集，手册说得很直白：“The attributes can have arbitrary values; however, various nix subcommands require specific attributes to have a specific value”。所以“schema”不是语言规定的，是 nix 命令各自的约定。nix flake check 的手册页把能被检查的列出来了，NixOS Wiki 的 Flakes 一页有一份带注释的 schema。我把它们和 Firn 对照成一张表（<sys> 是 x86_64-linux 这样的系统名，<n> 是任意名字）：

这张表里有三个规则要单独记。

第一，哪些带系统层。 packages、apps、devShells、checks、formatter、legacyPackages 的第一层是系统名；overlays、nixosModules、nixosConfigurations、templates 和 lib 没有。道理很简单：前一类是“构建出来的东西”，它们属于某个平台；后一类是“代码”（一个 overlay 是个函数，一个模块是个函数），平台在它被用起来的时候才确定。

第二，nix 命令怎么按名字找。 nix build .#hello 里的 hello 要变成一个完整的属性路径，规则在源码里：installables.cc 的 249 到 257 行，默认前缀是 packages.<当前系统>.，再退一步是 legacyPackages.<当前系统>.（源码里的注释把后者叫作“a temporary hack until Nixpkgs is properly converted”）。nix run 在前面多放了 apps.<系统>.，nix develop 多放了 devShells.<系统>.。这就是为什么 nix build .#mini.hello 这样的写法能成立：packages.x86_64-linux.mini.hello 不存在，退到 legacyPackages.x86_64-linux.mini.hello，它存在。

第三，nix flake check 认得的有哪些，认不得的怎么办。 flake.cc 的 425 到 464 行是 apps 的检查：必须有 type 和 program，meta 缺了会警告，除了这三个键再多一个就抛错 (app '%s' has unsupported attribute '%s')。检查的末尾，770 到 779 行，对不认识的输出名字发 unknown flake output '%s' 警告，但有一份白名单是“已知但不检查”的，里面有 lib、homeConfigurations、homeModules、flakeModules 这类社区约定的名字。所以 Firn 的 lib 不会被警告。

legacyPackages 的“legacy”经常被误读，nixpkgs 自己的 flake.nix 在205 到 223 行解释了：它是 packages 的替代名字，原因是 packages 会让 nix flake show nixpkgs “unusably slow”，因为 CLI 得判断每个属性是包还是子包集；换成 legacyPackages，CLI 只显示 omitted。这条解释马上就会在下面的 nix flake show 输出里兑现。

flake.lock：锁的是什么#

flake.nix 里写 nixos-unstable，就像菜谱上写“一袋面粉”：哪个牌子、哪一天的货，你不知道。flake.lock 是采购单：哪家超市的哪个货架 (rev)，称出来多重 (narHash)。采购单一旦写下来，下次不管超市今天进了什么新货，你拿到的还是那一袋。（这个比喻到 narHash 就不够用了：称重单是用来验货的，不只是记账。）Rust 读者可以把锁文件对应到 Cargo.lock，Pebble 第 1 篇里 workspace 共享的就是那一份。

纯求值#

flake.nix 的求值是纯的。这一节回答第 1 篇留下的那个问题。第 1 篇我看到 nix config show pure-eval 是 true，而手册里 pure-eval 写的默认值是 false，我“没有读源码”，猜是新命令的专门行为。现在读了：

  • pure-eval 这个设置的默认值确实是 false（eval-settings.hh 的 181 到 184 行），和手册一致；
  • 但 nix 这个命令在启动时，处理完 nix-build 这类旧命令之后，直接把它改成 true：main.cc 的 428 行，evalSettings.pureEval = true;；
  • 例外有两个：nix repl 是“默认不纯”的（repl.cc 的 55 行，main.cc 的 580 行据此把它改回 false），--file 也会把它改回 false（installables.cc 的 461 到 463 行，如果你显式写了 --pure-eval 就报错：'--file' is not compatible with '--pure-eval'）。

所以我的猜测对了一半：它确实是新命令的专门行为，而旧的 nix-instantiate、nix-build 根本走不到这一行。

为什么 flake 要这样？ 我的理解是：flake 的卖点是“同样的输入，同样的输出”。输入是源码树加锁文件。如果求值时允许读 currentSystem、环境变量、<nixpkgs> 这样的查找路径，结果就还取决于跑它的那台机器，锁文件就白锁了。所以纯求值才会连着 flake 一起出现，也才会有后面的 eval cache：只有求值是输入的纯函数，才能按输入的指纹缓存它的结果。

这还解释了本篇开头那个“样板”：为什么每个输出都要 forAllSystems。一个 flake 不能问“我在哪种机器上”（上面刚证明过），所以它只能把每个系统的答案都列出来，由 CLI 挑：nix build .#hello 查 packages.<当前系统>.hello，当前系统是 CLI 带进来的（installables.cc 的 253 行用的是 settings.thisSystem），不是 flake 自己去读的。表达式不能自己知道系统，才有了每个输出多出来的一层系统名。这是我把几处源码放在一起之后的理解，不是哪份文档的原话。

eval cache#

求值是纯的，就可以缓存。eval-cache 这个设置的手册描述只有几句：使用 flake 求值缓存；某些命令在第二次对某个版本的 flake 调用时不必再求值；中间结果不缓存；默认开启。我想量一下它到底值多少，同时发现一件和这三句不完全对得上的事。

缓存的键是 flake 的指纹。LockedFlake::getFingerprint（flake.cc 的 979 到 1002 行）把源码的指纹、子目录、锁文件的文本，以及 revCount 和 lastModified 拼起来取 SHA-256；锁文件里有没锁定的输入，就没有指纹，也就没有缓存。对 git 来源，指纹是提交哈希；工作区是脏的、又没有子模块的时候，是提交哈希加上改动文件的内容哈希（git.cc 的 1082 到 1107 行）。openEvalCache 只在 eval-cache 打开而且求值是纯的时候才算指纹。缓存本身是一个 SQLite 文件，放在 eval-cache-v6/<指纹>.sqlite，位置由缓存目录决定（eval-cache.cc 的 73 到 76 行）。

我先想到的解释是“outPath 是带字符串上下文的字符串，缓存不存这种东西”。源码不支持这个说法：AttrDb::setString 在写入时把上下文也存进去了（eval-cache.cc 的 139 到 157 行），读的时候再还原（266 到 270 行）。真正的原因在另一头，这是我读 2.34.9 的源码得到的解释：

  1. nix eval 的 run 调用 installable->toValue(*state)（eval.cc 的 67 行）；
  2. 对 flake 的 installable，toValue 是 return {&getCursor(state)->forceValue(), noPos};（installable-flake.cc 的 155 到 158 行）；
  3. AttrCursor::forceValue()（eval-cache.cc 的 394 到 426 行）对最后这个属性无条件地求值，求完之后如果缓存里还没有，把结果写进去；它不会先去读。

读缓存的是另一类函数：getString()（528 到 547 行）先 fetchCachedValue，命中了就返回。nix path-info --derivation 走的是 InstallableFlake::toDerivedPaths，里面调用 attr->forceDerivation()（installable-flake.cc 的 104 行），而 forceDerivation 取 drvPath 用的正是 getString()（eval-cache.cc 的 705 到 719 行）；注释里还说，如果缓存里的 .drv 已经被垃圾回收了，会强制重新求值。所以 nix path-info 能直接从缓存里读到叶子 drvPath，而 nix eval 只能读到沿路的中间属性集，最后那个属性总是重新求值。nix build 也是同一个 toDerivedPaths，应该同样受益；我没有给它单独测，这一句是从源码推的。

我对 flake 不满意的三件事#

写到这里，我对 flake 的日常使用是满意的：一个锁文件，一组命令都认得的输出名，一个不会被我的环境变量弄脏的求值。但上面的每个实验里都有一个让我皱眉的地方，我挨个说。

样板。 每个按系统展开的输出都得套一层 forAllSystems，Firn 里有 systems 列表、forAllSystems、pkgsFor 三个只为这一层服务的名字，连 devShells = nixpkgs.lib.mapAttrs (_: devShell: { default = devShell; }) devShells; 这一行（flake.nix 的 122 行）也是同一种样板换了个写法。nixpkgs 自己也这样：它的 flake.nix 第 12 行写的是 forAllSystems = lib.genAttrs lib.systems.flakeExposed;，flakeExposed 在锁定的提交里是 9 个系统。前面“纯求值”一节我给了这层样板的来由（表达式不能问“我在哪”），可知道来由不等于喜欢它：它让每个输出都深了一层，也让每个新手第一次读 flake.nix 时先看到的是一堆和他的项目无关的东西。

整份复制。 copy_to_store.sh 量的是 Firn 这种 170,536 字节、174 个文件的仓库，没什么感觉。但它的机制是整树复制，不管你求值时用到几个文件；Determinate Nix 的 lazy trees 就是冲着这个来的（上面已经引了它的文档），而 2.34.9 没有。我没有在大仓库里测，所以这一条我只能说机制是这样，代价有多大取决于你的仓库有多大。

仍然是实验性的。 上面已经引过：自 2.4 (2021-11-01) 起，手册里一直把 flakes 列在实验性功能下。我不知道上游为什么一直没有把它转正，也不打算猜；我能说的是它现在的状态：你要在 nix.conf 里手动开 experimental-features，手册会提醒你接口“subject to change”，而 nixpkgs 自己的 flake.nix 第一行还写着 “Experimental flake interface to Nixpkgs”。我的日常是建在它上面的，所以我有偏见；这个偏见的成本，是要接受这件事哪天可能变：一个“实验性”的东西，没有人答应你它不变。

flake-utils 与 flake-parts#

样板的问题有人解决了，两个最常见的方案我各说一段，Firn 两个都不用，继续用手写的 nixpkgs.lib.genAttrs。

flake-utils 是 numtide 的一个库。它的 README 一开头说目标是“a collection of pure Nix functions that don’t depend on nixpkgs, and that are useful in the context of writing other Nix flakes”。最常见的用法是 eachDefaultSystem：eachSystem 预先填上 defaultSystems（README 里写的默认值是 x86_64-linux、aarch64-linux、x86_64-darwin、aarch64-darwin），你写一个从系统名到属性集的函数，它替你把每个键下面的系统层搭好：README 的例子是 eachSystem [ system.x86_64-linux ] (system: { hello = 42; }) 得到 { hello = { x86_64-linux = 42; }; }。它和 Firn 的 forAllSystems 想法一样，区别是 Firn 是在每个输出上各写一次系统层，flake-utils 是在整个函数外面写一次、里面不再提系统。代价是多一个输入，多一个锁文件节点（README 还提到它本身有一个叫 systems 的输入，可以用 follows 覆盖，见前面的 follows 一节）。

flake-parts 是 hercules-ci 的一个框架，自称“Core of a distributed framework for writing Nix Flakes”。它的做法不一样：把 flake 的输出建模成模块系统的选项，所以你写的是 perSystem = { config, pkgs, ... }: { packages.foo = ...; };，加一个 systems = [ ... ] 声明要哪些系统，非按系统的东西放进 flake = { ... }，用 imports 把一个大 flake.nix 拆成几个文件。文档对自己的定位是“a minimal mirror of the Nix flake schema”，机制靠模块系统，这个会在第 15 篇讲，所以我这里不展开。

Firn 不用它们的理由很朴素：现在只有两个系统、一百多行、六个输出，我想把约定的那张表原样摆在眼前读；再往后，模块系统那几章会让我回头看这个选择，到时候我再说我对它的看法。

nixConfig#

四块里的最后一块 nixConfig 我一直没讲。手册说它是“a set of nix.conf options to be set when evaluating any part of a flake”，出于安全，只有一小组选项可以在没有确认的情况下设置（除非全局配置里打开了 accept-flake-config）：bash-prompt、bash-prompt-prefix、bash-prompt-suffix、flake-registry、commit-lock-file-summary。其余的（比如额外的 substituter）会让 Nix 问你一次。Firn 的 flake.nix 现在没有 nixConfig，因为它要等到第 20 篇的 CI：那时我要让 flake 带上 Cachix 的缓存地址，那是一个会让你信任别人的缓存的设置，所以到时候我会专门讲它为什么要你确认。

让我意外的事#

nix eval 的缓存是零，nix path-info 的缓存是十倍。 我一开始是用 nix eval --raw ...outPath 去测 eval cache 的，得到 1.2 倍，差点就写成“eval cache 在这里几乎没用”。换成 nix path-info --derivation 之后是 9.2 倍（481 ms 对 52 ms）。同一个缓存，nix path-info 能直接读到叶子 (drvPath)，nix eval 只能读到中间的 attrset，最后那个属性总是重新求值。如果不去读 eval-cache.cc 里 forceValue 和 getString 的区别，我会带着一个错误的印象走很久。

手册、配置和实际行为说了三种话。 手册的 pure-eval 一节说默认是 false；nix config show pure-eval 说 true；真正起作用的是 main.cc 的 428 行一句赋值，而 nix repl 又在另一个地方被改回去。第 1 篇里我猜这是“新命令的专门行为”。读完源码，对了一半：确实是 nix 命令自己的行为，而不是版本有意改了默认值。

锁定之后，ref 不见了。 original 里有 "ref": "nixos-unstable"，locked 里没有，多出来的是 rev、narHash、lastModified。我原来以为锁文件是“在原来的基础上补上一个提交哈希”，实际上它是“把分支名换成提交哈希”：钉住之后，分支叫什么已经不重要了。

改过没暂存的 flake.nix 可见，git 不认识的 extra.nix 不可见。 这条规则我背了七章，但从来没想过它的精确含义。实验里一个修改过没暂存的 flake.nix 被 Nix 读到了，一个根本没被 git 知道的 extra.nix 没有；而 git add 之后什么都不用提交，它就可见了。所以规则不是“提交过的文件”，是“git 知道的文件，取工作区里的内容”。

下一篇#

这一篇我们一直在用“新”命令：nix flake show、nix eval、nix run、nix path-info，它们都从 flake 的输出树里按名字找东西，也都顺带享受了锁文件和纯求值。但是你机器上还有另一套命令：nix-env、nix-build、nix-shell，它们不认 flake 的 schema，靠 <nixpkgs> 这样的查找路径和 channel 工作；第 1 篇里我们已经看到，同一台机器上的 <nixpkgs> 和钉死的 nixpkgs 是两个版本。下一篇，第 9 篇，两代 CLI：nix-env、nix-build、nix-shell 与 nix profile，我把两代命令并排摆开：同一件事新旧各怎么写，channel 到底是什么，nix profile 和 nix-env 的差别，以及它们各自留在磁盘上的 profile 和 GC 根。这一页 nix flake show 的树只有六个顶层输出，到系列结束的时候它会长得多，而每多一个输出，上面那张 schema 表里就会有一行被点亮。Firn 的 default.nix 和 shell.nix 会在那一章出现，让不认 flake 的旧命令也能读到你在这一篇里钉死的那份 nixpkgs。
