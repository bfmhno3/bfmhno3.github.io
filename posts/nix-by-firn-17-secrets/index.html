第 16 篇的“让我意外的事”里，我去查了 lab 主机的 initialPassword = "firn" 到底去了哪里：明文，在 store 里，权限 -r--r--r--。那个口令是我故意写成演示用的，无所谓，这一篇把问题倒过来问：如果它是真口令呢？我起了两台 NixOS 虚拟机，同一个令牌 correct-horse-battery-staple，一台把它直接写进 environment.etc，另一台用 sops-nix 从加密文件里在激活时解出来，然后在两台机器的系统闭包里数含这串明文的 store 路径：sops 节点 0 个，naive 节点 1 个（权限 444），而解密出来的文件权限是 400，落在 ramfs 上，服务只把 sha256 指纹打进日志。

本篇检查点

这一篇结束时，Firn 仓库的标签 ch17 里：nixos/modules/secret-demo.nix（33 行，services.firn-secret-demo）、nixos/tests/secrets.nix（81 行，两个节点的虚拟机测试）和 nixos/tests/secrets/ 下三个文件（age-key.txt 4 行、.sops.yaml 4 行、secrets.yaml 17 行，一把只给测试用的公开 age 密钥和它加密的文件）；flake.nix 多了 18 行、少了 1 行，多出一个 sops-nix 输入和 checks.x86_64-linux.secrets-vm，x86_64-linux 上的检查是 17 个（ch16 标签上是 16 个），flake.lock 从 2 个节点变成 3 个；lab/ch17/ 下 8 个 .sh 实验和 fixtures/ 里 2 个文件（其中 secrets_vm_host.sh 是 _host 实验，CI=true 时被跳过），env -u CI make ch17 通过（8 个 ok）。git diff --name-only ch16 ch17 列出 17 个文件，文件清单里一个不少。 涉及的概念：store 的可读性（444 的文件、.drv 里的环境变量、builtins.readFile、二进制缓存），解决方案的几个家族（激活时解密、systemd credentials、外部密钥管理），age 的格式与开销，sops 的文件格式与创建规则，age 与 GPG 的取舍，用 ssh-to-age 把主机密钥变成 age 密钥，sops-nix 的激活顺序、/run/secrets 与 ramfs，LoadCredential 与 DynamicUser，测试专用密钥，以及 agenix 的对照。 前置：第 16 篇：NixOS：services.cairn、VM 测试与一次 switch。NixOS 测试框架和 switch-to-configuration 怎样执行 activate 在那里讲过，这一篇直接用；store 路径的哈希在第 6 篇讲过，store 文件的 444 权限在第 2 篇里看到过，flake 的输入和锁文件在第 8 篇讲过，模块的选项和 mkIf 在第 15 篇讲过。 终稿与否：nixos/modules/secret-demo.nix、nixos/tests/secrets.nix、nixos/tests/secrets/ 和 lab/ch17/ 在这里就是终稿；flake.nix 和 flake.lock 之后的章节还会改（还会加输入）。

整篇的中心思想只有一句：store 是公开的，所以密文可以进 store，密钥和明文不可以。 其余所有东西，包括 sops 的文件格式、age、ssh-to-age、激活顺序、为什么 /run/secrets 不是 store 路径，都是这句话的推论。

环境#

这一篇所有输出来自这台机器：NixOS 26.05 (Yarara)，Linux 6.18.60，x86_64，上游 Nix 2.34.9，/dev/kvm 存在。nix develop 里的工具是 sops 3.13.3、age 1.3.1（age 和 age-keygen 都打印 v1.3.1）、ssh-to-age 1.3.0（版本取自 store 路径名，它的 -version 打印的是 dev）和 OpenSSH_10.6p1。Firn 钉的 nixpkgs 是 56c02bc00adcf003215cc4bd996d6efaf4cff188；sops-nix 钉在 a8627b21b9107c5711c96b84f32a9a4b3d45295f，2026-08-13 的一个合并提交，我用 GitHub 的提交列表核对过，到 2026-08-23 为止（也就是 nixpkgs 那个锁的日期）它是 master 上的最后一个。文中引用的 nixpkgs 行号是 56c02bc 上的行号，sops-nix 的行号是 a8627b2 上的，我在本地那两份源码上逐条核对过，链接指向同一个 rev。

我的 shell 里设了 CI=true，Firn 的运行器会据此跳过名字以 _host 结尾的实验。lab/ch17/ 里只有一个，secrets_vm_host.sh，所以我按惯例跑 env -u CI make ch17，在 nix develop 里，整条命令（含 nix develop 的启动）花了 109.618 秒，8 个实验全部 ok。虚拟机测试的结果在这之前已经在 store 里，所以 secrets_vm_host.sh 走的是 --rebuild 分支，开头那个块里的 volatile: wall time: 102 s 是这个分支的墙钟时间，不是第一次构建的时间；每次跑都不同，只当作一个样本。

实验分两类。一类在 lab/ch17/ 里，我给出文件路径、摘录和 out/ch17/ 里的真实输出。另一类是我为了回答某个问题当场敲的，每一条都标着“（手敲，不在 lab/ch17/ 里）”，输出同样是真跑出来的，命令都假设你在 ~/firn 里。其中三个 Nix 文件放在 /tmp/scratch17/ 下：probe_vm.nix 和 probe_tmpfs.nix 是两个借 secrets-vm 改测试脚本的虚拟机探针，keyfile_in_store.nix 是一个只求值的小配置；三个都过了 nixfmt --check，内容贴在用到它们的小节里。两个探针靠 builtins.getFlake 把 Firn 当 flake 读进来，所以要加 --impure，路径用 --argstr firnPath "$PWD" 传，不用环境变量。

还有一条规矩，因为这一篇的主题是密钥：仓库里唯一的私钥是 nixos/tests/secrets/age-key.txt，它是我为这个测试生成的、故意公开的那一把，第一行注释就写着 TEST ONLY。实验里的其他密钥全是 age-keygen 或 ssh-keygen 在临时目录里现生成的一次性密钥，用完随目录删掉。我没有读我自己的 ~/.ssh 和 ~/.config/sops；需要“没有任何密钥可用”的场景时，我把 HOME 指到一个不存在的目录。这一篇也不会贴任何私钥的内容。

威胁模型：store 里的东西谁都读得到#

第 6 篇讲过路径名是内容的哈希，第 2 篇里我量过 store 文件的权限是 444：同一个路径任何用户、任何构建都能直接拿去用，这是 Nix 能共享构建结果的前提。翻译成安全的语言只有一句：store 没有访问控制。 这是设计，不是漏洞。我只用这一次比喻：store 像小区门口的公告栏，谁路过都能读，所以能往上贴的只有锁好的信，不能是信本身。

接下来五个实验，每一个砍掉我自己曾经有过的一种“这样应该没事”的想法。

想法一：写进 store 的文件，别人读不到#

lab/ch17/store_world_readable.sh 用 writeText 把一个“口令”写成 store 文件，然后看权限：

权限 444，属主是 root:root（写进 store 的是守护进程）。444 的意思是三类用户都有读位：本机上任何一个账号、任何一个服务，只要能跑 cat，就能读到 hunter2-firn-lab。脚本里那行 read as another user would 是我在自己的 shell 里 cat 的，并没有切换用户（所以严格说，它只证明了我能读自己的文件，hah）；真的换成 nobody 去读，我放在“/run/secrets：符号链接，加一个 ramfs”那一节做。这个文件会一直待到垃圾回收把它清走为止（垃圾回收在第 9 篇量过），也就是说，写进去之后再删掉配置，口令并不会跟着消失。

解法的几个家族#

五个实验之后，要求其实只剩一条：明文只在运行时出现，而且不经过 store、不经过 Git、不经过缓存。 我知道的做法分四类，每一类的取舍是“钥匙放在哪里、明文什么时候出现”：

家族密文在哪钥匙在哪明文什么时候出现代价
带外文件没有密文，文件本身无你手工 scp 的那一刻没有 Nix 参与，配置里只有一个路径字符串；重装机器要自己记得补文件
激活时解密 (sops-nix, agenix)Git 和 store 里目标机器上的一把私钥系统激活时，写进 /run要管理这把私钥怎么到达机器；密文 444 地躺在 store 里，安全完全取决于私钥
systemd credentials单元文件里 (SetCredentialEncrypted=)，或磁盘上的加密文件 (LoadCredentialEncrypted=)，或根本没有（LoadCredential= 读一个已存在的文件）机器上的 /var/lib/systemd/credential.secret，或 TPM2服务启动时，进服务私有的目录密文绑定一台机器，在别处生成不了；明文文件从哪来还是要解决
外部密钥管理（Vault、OpenBao、云厂商的 KMS）不在仓库里在服务端，凭身份访问应用运行时去取多一个要运维的服务；我这篇没有运行它

第一类是所有别的方案的底线：只要你愿意手工放文件，LoadCredential = "token:/var/lib/firn/token" 就够了，store 里只有一个路径字符串。它的毛病是不可重现，这正是我们用 Nix 想摆脱的状态。第二类是这一篇的主角，因为它是唯一一种能把密文放进配置仓库、让整个系统仍然是“一个表达式的结果”的做法。第三类和第二类不冲突，而是下游：sops-nix 把明文放在 /run/secrets，服务再用 LoadCredential 把它拿走，这正是 secret-demo.nix 做的事，“写一个用这个密文的服务”那一节会看到。第四类我没有运行过，只留一个和这一篇有关的事实：sops 自己可以用 AWS KMS、GCP KMS、Azure Key Vault 和 HashiCorp Vault 当“主密钥”（见 sops 的 README 和文档），也就是把“谁能解开数据密钥”这件事交给密钥管理服务的访问控制，这一点我读了文档，没有试。

systemd-creds 这一类，我在虚拟机里敲了一遍往返，输出放在“虚拟机里的 systemd-creds”那一节：一个 28 字节的令牌加密之后是 171 字节，解密回来是同一个令牌，systemd 还顺便警告它用来加密的 credential.secret 不在加密介质上。它解决的是另一个问题：怎么把一个已经在机器上的东西安全地交给某个服务，而不是怎么把它安全地送到机器上。

为什么是 age，不是 GPG#

sops 同时支持 age 和 PGP。我不是 GPG 的专家，所以这一节的取舍主要引用别人的话，自己只量了一个尺寸。sops 文档的 age 一页说：“It’s recommended to use age over PGP, if possible.” 它的安全页把“PGP 密钥常常被误用，要么主人把它从一台机器拷到另一台，要么忘在一台没人用的机器上”列为一个威胁。age 的 README 用一句话描述自己：small explicit keys, post-quantum support, no config options, and UNIX-style composability。我从这几句话里读出的取舍是：age 没有钥匙环、没有信任网、没有配置，一把密钥就是一个 189 字节的文本文件，所以把它放进一个激活脚本、一个测试夹具或者一个 ramfs 都很简单；代价是它没有 GPG 那套撤销和过期的机制（这一点是我从“没有配置”推出来的，没有查证）。要注意，安全页开头有一条维护者的说明：这一部分由 SOPS 的原作者在 Mozilla 工作时写成，保留是出于历史原因，“not necessarily representative of the views of the current maintainers”。所以那条 PGP 的理由我只当作历史背景，不当作现在的结论。

主机密钥：ssh-to-age#

到这里还缺一环：解密用的私钥放在目标机器的哪里，怎么放进去。sops-nix 的第一个回答是：用机器已经有的东西。每台开了 sshd 的 NixOS 机器都有一把 ed25519 的主机密钥，ssh-to-age 能把它的公钥变成一个 age recipient，把私钥变成一个 age identity。lab/ch17/ssh_to_age.sh 在临时目录里造一把一次性的 ed25519 密钥来演示：

三个要点。一是公钥这半边是公开信息，所以 ssh-keyscan 一台远程机器就能拿到它的 recipient，不需要登录（ssh-to-age 的 README 的例子就是这么用的，我这里没有扫任何机器）。二是私钥这半边，输出里只打印了 AGE-SECRET-KEY- 这个前缀，脚本没有把它打出来；它被写进临时文件，再用 age-keygen -y 算回公钥，和直接转换的公钥比对相等，才说明“两个视图是同一把密钥”。三是 age 真的拿它解开了东西：host secret 是用转换出来的 recipient 加密、转换出来的 identity 解密的往返。

顺带一提，sops 自己的文档说它现在也能把 ssh-ed25519 AAAA... 直接当 recipient、用 ~/.ssh/id_ed25519 解密（见 age 一页），sops-nix 的源码里还有一条注释，说 sops 3.10 起会无条件去 $HOME/.ssh/ 找 ssh 密钥（modules/sops/default.nix 的 L33 到 L41，所以激活时它把 HOME 设成 /var/empty）。这一篇走 ssh-to-age 这条路，因为 sops-nix 的激活代码就是这样处理主机密钥的；直接用 ssh 公钥当 recipient 那条路我没有试。

sops-nix 里对应的是两个默认值。sops.age.sshKeyPaths 的默认值是“services.openssh.hostKeys 里类型为 ed25519 的那些”（modules/sops/default.nix 的 L182 到 L191 是 defaultImportKeys，L364 到 L371 把它接到这个选项），它同时排除了落在 /run/secrets 下的路径，以免“密钥本身要靠 sops 来部署”这个死循环。激活时，sops-install-secrets 对每一个这样的路径读私钥、转成 age 密钥，追加进一个文件：importAgeSSHKeys 里调的就是 agessh.SSHPrivateKeyToAge。这个文件放在 ramfs 挂载点里（/run/secrets.d/age-keys.txt，虚拟机里能看到它），不放在磁盘上。

我没有在真机上走一遍“新机器接入”的流程，以下是我读文档和源码得到的理解，不是我做过的实验：新机器第一次启动，sshd 生成主机密钥；你用 ssh-keyscan host | ssh-to-age 拿到它的 recipient，写进 .sops.yaml，对已有的文件跑 sops updatekeys，让每个文件的数据密钥多包一份给新机器；重新部署，机器激活时就能解开。这里有一个鸡生蛋的环节：在新机器第一次启动之前，没有主机密钥，就没有 recipient，也就不可能有“第一次启动就带着正确密文”的镜像（除非你预先把一把你控制的密钥放进镜像，这就回到了“密钥怎么到机器上”这个问题本身）。主机密钥丢了也是同样的问题：它是这台机器的信任根，重装系统时不保留 /etc/ssh，旧密文就解不开，得靠别的 recipient（比如你自己的密钥）来解开再换新的。

参考答案

（手敲，不在 lab/ch17/ 里）

纯求值（flake 的默认模式，第 8 篇讲过）直接拒绝读任意绝对路径，所以 flake 里不可能通过这条路把运行时的明文读进配置。反过来，一旦加了 --impure，在恰好存在这个文件的机器上（比如你部署用的那台），readFile 就读得到，读出来的字符串再插进 writeText 或者任何会进 store 的东西，就回到“想法三”。所以规矩是：永远只传路径字符串，不要读它的内容。这是我对机制的推断，只验证了纯求值那一半的报错，--impure 那一半沿用了“想法三”的实验。
