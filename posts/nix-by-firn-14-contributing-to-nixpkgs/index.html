这一篇停在哪里#

先把边界说清楚，因为这个话题最容易写成“教你怎么提交”。我没有提交。我做的事是：

  • 在 ~/.cache/firn/nixpkgs 里建了一个深度为 1 的 nixpkgs 工作树，两个分支，firn-base 在钉住的 rev 上，firn-cairn 在它之上多一个 commit。
  • 用 nix-build、nixpkgs-vet、nixf-diagnose、nixpkgs-hammer、nixpkgs-review 检查这个 commit。
  • 读 CONTRIBUTING.md 和 pkgs/README.md，查 branch 和 channel 的实际状态。

我没做的事：fork NixOS/nixpkgs，加自己的 remote，把分支推上去，开 PR。git remote -v 里 origin 的 fetch 和 push 地址都是 NixOS/nixpkgs.git 本身，没有 fork；让 git push 不发生的是脚本里没有这条命令（整份脚本里 push 这个词只出现一次，在注释里）。真要提一个 PR，CONTRIBUTING 的流程是先 fork，克隆这个 fork，把上游配成另一个 remote，最后推到 fork（第 33 到 36 行与第 81 到 84 行）。

Cairn 也不应该被提交。pkgs/README.md 在“新增一个包之前”列了五个问题，其中一个是“这个包会被别人用到的可能性有多大”，一个是“你愿不愿意至少维护它一个完整的 Nixpkgs 发行周期”（第 30 到 50 行）。Cairn 是我自己的 0.1.0 备份脚本，我对这两条的诚实回答都是“不确定”。所以这一篇是演练：流程是真的，输出是真的，只是终点停在我自己的磁盘上。

规则：RFC 140#

这套结构出自 RFC 140(Simple Package Paths)，作者 Silvan Mosberger，RFC 的 PR 140 在 2023-07-12 合并。它要检查的东西列在 RFC 的“File structure”一节（第 52 到 56 行）：

  • pkgs/by-name 下只能有 ${shard}/${name} 形式的子目录，叫 package directory。
  • 同一层里的 name 转成小写后必须唯一。
  • name 只能由 ASCII 字符 a-z、A-Z、0-9、-、_ 组成。
  • shard 是 name 的小写前两个字母，RFC 用 Nix 写成 shard = toLower (substring 0 2 name)。
  • 每个 package directory 里必须有 package.nix，可以有别的文件。

RFC 在“Semantics”一节还要求 CI 检查：package.nix 不能访问自己目录之外的文件（第 75 行）。by-name 的 README 说了这条带来的后果：给一个已有的多版本包（foo_1、foo_2 共用目录外的文件）再加一个实例，会同时撞上“新顶层包必须走 by-name”和“by-name 不能引用目录外文件”两条，README 建议先用 inherit 的写法绕开（第 134 到 165 行）。Cairn 是单个包，所有文件都在自己的目录里，碰不到这条。

它不是所有包的归宿#

README 写得很清楚，pkgs/by-name 有两条限制（第 107 到 121 行）：只能放用 pkgs.callPackage 定义的包，所以 pkgs.python3Packages.callPackage ... 那一类不行；只能放顶层包，所以 pkgs.pythonPackages.* 这样的包集合不行。同时它又说：新包应当“尽可能”用这个机制（第 4 行）。所以在 nixpkgs 里加一个顶层的普通包，没有选择，就是 pkgs/by-name。Cairn 满足两条：它是顶层包，callPackage 就能调。

还有一个把它和合并流程绑在一起的条件。CONTRIBUTING.md 描述了一个可以在评论里叫的合并机器人，@NixOS/nixpkgs-merge-bot merge，它会逐条验证，不满足就拒绝：PR 作者是 @r-ryantm 或 committer，触发它的人是目标分支上该包的维护者，包在 pkgs/by-name 里（第 328 到 333 行）。by-name 的 README 在“迁移”一节里也引用了这一点：只有 pkgs/by-name 里的 PR 才能被自动合并（第 81 行）。所以一个没有维护者的新包用不上它；这一条我没有试，是读文档得出的。

strictDeps = true 关掉 stdenv 对依赖放错列表的宽容。Nixpkgs 手册说，原生编译时 stdenv 对依赖放进错误的列表很宽松（运行时要用的依赖放在 nativeBuildInputs 里也能用），这会破坏交叉编译，打开 strictDeps 就不再宽容（stdenv 章节第 490 到 494 行）。第 12 篇做过交叉编译，所以这条的原因你已经见过了。

pkgs/README.md 规定了提交信息的形状（第 171 到 191 行）：

提交之后，CI 做什么#

PR 一旦开出来，你看不到的那一半就开始了。.github/workflows/pull-request-target.yml 的名字是 PR，它的任务有 Check、Lint、Eval、Bot、Build（第 74 到 140 行）。我挑和 Cairn 有关的：

  • Lint 里有四个任务：treefmt（格式，用 nixfmt）、parse（解析所有 Nix 文件）、nixpkgs-vet（lint.yml 第 89 行），还有刚才说的 commits。.github/workflows/README.md 说必需的检查由这个 PR 工作流定义（第 69 到 70 行），所以我手敲让它报 NPV-164 的那个检查，在 PR 里就是一个要过的关；失败时它还会打印本地怎么跑。
  • Eval 在 PR 的合并 commit 和目标 commit 上各求值一遍所有系统的输出路径，再比较（eval.yml 第 201 到 246 行）；把结果摘要写进一个叫 Eval Summary 的提交状态，内容是“Package: added N, removed N, changed N”加上 linux 和 darwin 各自的重建数（第 317 到 355 行）；如果 PR 指向了不合适的分支，它还会请求修改（第 372 到 383 行）。这是 nixpkgs-review rev 在我本地做的那件事（求值两遍，做差）的服务端版本。
  • Build 构建的是 shell、手册、lib-tests 和 tarball（build.yml 第 38 到 46 行），不是你的包。包的构建是另一回事，见下一段。

最后是人。pkgs/README.md 的“新包”审稿流程一共十几条（第 1219 到 1247 行）：路径、名字、版本是否合规；提交信息是否合规；源码是否来自官方位置、是否用了合适的 fetcher；meta 的许可证是否和上游一致，platforms、maintainers、mainProgram 是否设了；特殊的打包选择有没有注释；有拼写错误报告；本地构建；运行每个可执行文件。这些里，机器能帮忙的是 vet、nixf-diagnose、hammer 和 review，剩下的（许可证对不对，注释说没说清楚，维护者愿不愿意）只有人能判断。我没有测过一个 PR 从开出来到有人回复要多久，这个量要真提了才有，我不提，所以这个数字这一篇里没有。

那些改动应该进哪个分支？CONTRIBUTING.md 的“Branch conventions”给了决策树（第 449 到 470 行）：先问这个改动能不能进发行版，不能就 master；能而且 master 和发行分支上实现一样，就进 master 再回移；如果引起大规模重建，就走 staging。“大规模”没有正式的定义，CI 会按重建数量自动打标签，经验法则是 500 个以上考虑 staging，1000 个以上必须走 staging（第 496 到 497 行）。

staging 本身是个批处理机制：引起大规模重建的 commit 先进 staging，Hydra 不直接构建它；定期手动合并到 staging-next，Hydra 构建 staging-next 这个 jobset，验证没有大问题后，staging-next 再通过一个 PR 合进 master（第 370 到 373 行）；同时 master 自动合进 staging-next，staging-next 自动合进 staging，这两个自动合并由 periodic-merge-6h.yml 和 periodic-merge-24h.yml 实现（第 377 到 378 行）。Cairn 是一个叶子包：nixpkgs-review 报告说只新增 1 个包，没有任何已有包被它重建，所以它走 master，不涉及 staging。

Hydra：谁说了算#

channel 什么时候前进，不是人决定的。nixos/release-combined.nix 的文件头直接写着（第 1 到 3 行）：

“每当 tested 这个任务成功，并且其他任务都跑完了（它们可以失败），channel 就更新。”tested 是一个聚合任务，在同一个文件的第 54 行，它的 constituents 列表从第 70 行持续到第 220 行：nixos.channel，最小 ISO，图形 ISO，手册，加上一长串 NixOS 测试（acme、boot、chromium、docker、firewall、gnome、installer 的各种分区方案……）和几个必须能构建的软件包，比如 firefox-unwrapped。聚合任务的所有成员都构建成功，它才成功。所以 nixos-unstable 要求的是：整套 NixOS 的关键测试在这个 commit 上都过。

对应 nixpkgs-unstable 的是 pkgs/top-level/release.nix 里的 unstable 聚合任务（第 165 到 185 行），描述是 “Release-critical builds for the Nixpkgs unstable channel”，成员比 tested 少得多：源码 tarball、release 检查、metrics、手册、lib 的测试，加上 stdenv、cargo、go、linux、nix、pandoc、python3 这几个有代表性的包，以及刚才提过的 nixpkgs-review。这段列表里没有 NixOS 的集成测试。

两个 channel 的区别，nix.dev 的 FAQ 写得很清楚(Which channel branch should I use?)：nixos-* 指向的 commit，大部分 Linux 包已经预先构建好、可以从二进制缓存拿，而且通过了完整的 NixOS 测试套件；macOS 用 nixpkgs-*-darwin；*-small 通过的是更小的测试套件，所以更新更及时，稳定性保证更少。

如果 Cairn 想进 26.05，它不会自动去。CONTRIBUTING.md 的“How to backport pull requests”（第 244 到 278 行）有两条路：

  • 自动。 给 master 上已合并（或者还开着）的 PR 加一个 backport release-26.05 标签，一个 GitHub Action(backport.yml)几分钟后会开一个到 release-26.05 的新 PR。但是只有 Nixpkgs 维护者才能这样做（第 249 到 256 行）。我没有这个权限，所以对我来说这条路不通。
  • 手动。 走和普通 PR 一样的流程，只是本地分支和 PR 的 base 都用 release-26.05（第 262 行）；用 git cherry-pick -x 把 master 上的 commit 摘过来，原因不明显时用 -xe 加一句理由（第 268 到 270 行）；PR 描述里要链回 master 上的原 PR，标题带上 [26.05]（第 277 到 278 行）。

文档里有一个醒目的警告：不要用 nixos-YY.MM 分支，因为它“指向最近一次测试过的 channel commit”（第 264 到 266 行）。分支一节的 ls-remote 已经把这件事摆出来了：nixos-26.05 在 7dcdd8737，release-26.05 在 daeef707f，后者领先 237 个 commit。往 nixos-26.05 摘，起点就落后 237 个 commit；更要紧的是，那个分支是随 channel 更新的，不是给人推的。

能不能回移，取决于改动种类。CONTRIBUTING.md 第 482 行把“新的包、模块和函数”列在可以回移的改动里。新包回移时，by-name 目录也得在 release-26.05 上存在：RFC 140 的第一个 PR 特地写了，它“会被回移到稳定版，以保证新包的回移能工作”（RFC 第 45 行）。我用 gh api 看了一眼 release-26.05 上的 pkgs/by-name：

nixpkgs 里的包大多不是人手升级的。pkgs/README.md 说社区机器人 r-ryantm 会定期尝试更新所有包，运行 nixpkgs-update，找新版本、改文件、开 PR；设了 passthru.updateScript 的包，更新步骤更可靠（第 912 到 918 行）。我手敲数了一下这个习惯有多普遍（只数 pkgs/by-name 下的 package.nix 文件）：

实验的最后一段把这个后果量了出来：升级之后单独构建 cairn.tests.version，退出码 1，信息是 Version string '10' not found!，输出是 cairn 0.1.0。这正是 testVersion 的两个默认值（包自己的 version 和 <mainProgram> --version）该干的事：版本一漂移，测试就红。如果当初 version 写成字面量 "0.1.0"，这个测试会通过，漂移就没人发现；这是用默认值的理由。真正的修法在 nix-update 一侧：nixpkgs 里 4744 个文件用的是 tag = "v${finalAttrs.version}"，上游标签要是 v0.1.0 这种形状，nix-update 才知道同时改 version 和源。Cairn 仓库的标签是 chNN，我不改它们。

让我意外的事#

求值器不检查 by-name，CI 检查。 把 cairn 放进 pkgs/by-name/cr/cairn，nix-build -A cairn 照样能用；拦它的只有 nixpkgs-vet 的 NPV-142。overlay 文件头自己写着“不做校验，校验交给 CI”。

nixpkgs-hammer 的 no-build-output 条件看起来写反了。 变量叫 names_without_outputs，过滤的却是输出已存在的属性：构建过的 cairn 被说成“还没构建”，输出不在 store 里的变体什么也不说。实验的输出因此取决于我的 store。

升级工具会让版本号和源脱节。 nix-update 在 chNN 标签上不报错，只把 version 写成 "10"；是 testVersion 的默认值把它抓了出来，实验把这个失败打印了出来。

channel 的节奏和 checkinterval 同量级。 nixos-unstable 中位每 59.9 小时前进一次，nixpkgs-unstable 每 12.2 小时，和 Hydra 的 checkinterval（40.8 小时和 8 小时）量级对得上（我猜是它决定的，没有验证）；而 nixpkgs-review 本身就是 nixpkgs-unstable 聚合任务的一个成员。
